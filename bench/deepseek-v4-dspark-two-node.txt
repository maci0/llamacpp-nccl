--- where the gap is ---

The reference (vLLM refg, anemll 0.1.1, DSpark, TP=2, same pair, same protocol) is
63.1 / 112.1 / 140.9 / 156.0 at c1/c3/c5/c6, and its own step counters put c1 at 74.9 ms per
step and 4.70 tokens per step. This run is 4.41 tokens per pass at 43.1 ms per token, that is
190 ms per pass. So the two engines verify a comparable number of tokens per step; the gap is
per-step cost, 2.5x, and it is not an acceptance problem.

The per-pass cost of the layer split is bounded below by the target's own weight traffic. Decode reads
roughly 6 GB of active weights per token: 7 of 256 experts per layer at MXFP4 (137.06 of the file's
144.44 GiB is MXFP4, measured from the shards with gguf-py), plus attention and the Q8_0 output head.
A layer split puts node A's half and node B's half in series, not in parallel, so a token pays one
node's full pass over that traffic. Upstream llama.cpp gets 169 GB/s on this same box for the same
MXFP4 MoE shape (gpt-oss-120b: 59.02 GiB, 116.83 B total, tg32 58.72 tok/s in
benches/dgx-spark/dgx-spark.md, which is 2.87 GB of active weights per token), and that rate puts the
floor for this model near 35 ms per token before any draft work.

Measured here: 67.6 ms per token with no draft, 43.1 ms per token at n_max 15, against the 15.9 ms
per token the reference needs. The tensor-parallel path that would make the two nodes work on the
same token is implemented (see bench/glm53-split-detail.txt and the SESSION_STATE history on spark1)
but is allreduce-latency bound over this RoCE link: 12.8 tok/s without a draft and 21.9 tok/s with
the DSpark draft, both `llama-cli` at 2048 ctx, i.e. no better than the layer split. llama-server
could not be used for a like-for-like TP arm on 2026-09-13: llama_params_fit is not implemented for
SPLIT_MODE_TENSOR, so the load did not finish inside the run's timeout.
