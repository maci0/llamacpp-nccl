Two GB10 over ggml-rpc-server, tensor parallel, DeepSeek-V4-Flash-0731 UD-Q4_K_XL with the DSpark
draft. This file is about the coordination cost of that configuration: what the message counters say,
one change that was expected to be big and is not, and what that leaves.

--- the message counters ---

The RPC server prints per-connection totals when the client disconnects:

    [~rpc_server] connection stats: graph_compute: N, graph_recompute: M, post_allreduce: K

`graph_compute` means the client serialized the whole subgraph onto the wire and the server rebuilt it
(tensors, names, hash maps) before it could run; `graph_recompute` means the client reused a uid the
server already had and sent a small message instead. Two sessions, both DSpark, same build:

| session | generated tokens | graph_compute | graph_recompute | post_allreduce |
|---|---|---|---|---|
| c1/c3/c5/c6, 3 reps each | ~30700 | 58168 | 152511 | 199272 |
| c1/c3, 3 reps each | ~8200 | 16472 | 75823 | 88534 |

Per generated token, both agree to within 6 %: **1.9 and 2.0 full serializations**, 6.9 and 11.3
subgraph executions, 6.5 and 10.8 allreduces. The subgraph and allreduce figures differ between
sessions because the mix of concurrency levels differs: a pass is ~88 to 110 subgraphs whatever the
batch, so a level that carries more tokens per pass shows fewer subgraphs per token.

Two things follow. First, an allreduce per subgraph confirms the shape of the tensor-parallel path
(one collective at each subgraph boundary), and the ~2 full serializations per token mean the
serialize-and-rebuild path is at most a few percent of a token even at a pessimistic half a
millisecond each. That deprioritises an obvious-looking fix (making the graph uid stable so identical
graphs hit the server cache) to about 2 to 5 %.

--- the change that was expected to be big, and is not ---

In `ggml_backend_sched_compute_splits` (`ggml/src/ggml-backend.cpp`), before starting a split the
scheduler drains the backend that produced the previous split whenever the new split has no inputs to
copy and sits on a different device:

    if (split->n_inputs == 0 && prev_backend_id >= 0 && prev_backend_id != split_backend_id) {
        ggml_backend_event_synchronize(...) or ggml_backend_synchronize(sched->backends[prev_backend_id]);

A tensor-parallel graph alternates devices on almost every split and, after an allreduce, both devices
already hold the reduced tensor, so the next split needs no copy. If that drain fires, it waits on a
CUDA stream that also has the collective queued behind it, which would serialise the two nodes exactly
as the layer split is serialised. The earlier profile of this path found the client's CPU spinning in
`cudaStreamSynchronize`, which is what that wait would look like.

Tested by gating the drain on `GGML_SCHED_NO_DRAIN=1`, rebuilt into the client only (the RPC server
runs one backend, so it has no such transition), same flags as the published run:

| level | drain on (baseline) | drain off |
|---|---|---|
| c1 | 34.3 (31.4 - 36.3) | 34.7 (32.8 - 37.4) |
| c3 | 62.4 (60.0 - 63.8) | 58.9 (58.8 - 64.8) |

Three reps per cell, gates identical in both (` Paris. The capital of Spain`, `72, 9x9`). The two c1
ranges overlap by a third of their width and the c3 result is if anything slightly worse, so the drain
costs nothing measurable. Reverted: the change was applied to the client only, and the client tree and
the dev tree match by md5 (493ccfd74ad8266340512556f2940c23). Found while reverting: the peer's tree
carried an older copy of an unrelated hunk in the same file (the `if (ggml_nelements(ids_tensor) == 0)
continue;` guard in the offloaded-MoE copy path). It has been synced and the peer's rpc server rebuilt,
so both nodes now build from the same sources.

--- what that leaves ---

The pass at c1 is 131 ms for 4.50 accepted tokens, of which 20.6 ms is drafting (`bench/
deepseek-v4-tp-server-two-node.txt`). Of the remaining ~110 ms, the measured marginal cost of a token
inside the batch is 8.75 ms (from the one/five/sixteen/sixty-four-token passes), so about 52 ms of the
110 is the weight traffic the six-token verify must read, the MoE path runs at roughly 85 % of what the
part can move (`bench/deepseek-v4-op-profile.txt`), and roughly 2 % is the serialize-and-rebuild path
above. That accounts for the pass without a large unexplained term, which is a different conclusion
from the one this work carried a day ago: the earlier arithmetic attributed ~25 ms per token to
"per-subgraph host and launch work", and the two candidate mechanisms for it (the scheduler's
cross-device drain, and graph re-serialization) are now measured as small.

The one large, isolated, unexamined item left is the draft: 20.6 ms of every 131 ms pass, for a
one-layer MoE model that has to cross the RPC link on both of its decodes. `-devd CUDA0` cannot be used
(the `output_replicated` interaction aborts in the scheduler), but `-otd` (`--spec-draft-override-tensor`)
can move the draft's tensors onto CUDA0 without changing its device list, which avoids that abort. That
said, the draft is a four-layer 256-expert model (`offloaded 4/4 layers`), so at a six-token block it
reads on the order of 1.5 GiB of expert weights per decode, more than half of its 20.6 ms. Pinning it to
one device would double its per-node traffic rather than remove it, so that arm is now expected to come
out neutral or worse and has not been run.

--- 2026-09-14, what one decode actually sends ---

The peer's `GGML_RPC_DEBUG=1` log, over two c1 runs of the standard workload (about 4120 generated
tokens), counts the requests after the model load:

| request | count | per token | per pass (4.4 tokens) |
|---|---|---|---|
| `graph_recompute` (uid reuse) | 72527 | 17.6 | 90 |
| `set_tensor` | 43926 | 10.7 | 47 |
| `graph_compute` (full serialize) | 11721 | 2.8 | 12.5 |
| `memset_tensor` | 3224 | 0.8 | 3.4 |

Two things stand out. The full-serialization share is 14 % of the 84248 graph submissions, consistent
with the per-token counter figures above. And there are 47 tensor writes per pass, of which 63 % are
under 1 kB and none is over 1 MB; each of those hits `rpc_sync_backends` in our own patch, which drains
the peer's CUDA device before the write.

Tested by making that drain skippable (`GGML_RPC_NO_SYNC=1`), which is unsafe by construction because
the write can then race a queued graph:

| c1, three reps | median | range |
|---|---|---|
| drain on, same session | 37.6 | 35.9 - 37.6 |
| drain on, second run, same session | 35.6 | 33.9 - 36.6 |
| drain off | 36.5 | 34.2 - 36.7 |

So the 47 drains per pass are not the bottleneck either, and the gates still pass without them, which
means the races they prevent are not being exercised by this workload. Reverted; `ggml-rpc.cpp` is back
to the +19/-2 async-server patch and both trees match.

The same run also measured the cost of the peer's own request logging, because `GGML_RPC_DEBUG` writes
a line per request: logging on gives 37.6 and 35.6 at c1, against 34.3 with it off. If the peer's
request path were the critical path, adding per-request I/O would have shown up as a loss. It did not.

stay valid instead of being invalidated when allocations move. It was never A/B'd on the tensor-parallel
path, and a per-step graph re-capture in each of ~100 subgraphs would have looked exactly like the
per-pass overhead this work keeps chasing. Both nodes set, everything else identical:

|---|---|---|---|
| c1 | 34.7 | 33.0 - 37.1 | 11.7 % |
| c3 | 61.8 | 61.0 - 65.7 | 7.6 % |

Inside the band of every other run of this configuration (c1 34.3 to 37.6, c3 58.9 to 62.4), so no

    CUDA graph warmup reset:     8875

`reused` is the fast path taking the uid match, about 5 times per token; `warmup reset` is the graph

--- what the pass is actually made of, and why this is not a tuning problem ---

The two-node tensor-parallel pass at c1 is 125 ms for 4.5 accepted tokens. Its *marginal* token is
efficient: 8.75 ms per extra token against 1.6 GiB of per-node weight traffic, which is 196 GB/s per
node against the 232 GB/s this pair measures as achievable. The *fixed* part of the pass is the
problem, about 86 ms, and at a one-token batch the same engine spends 43 ms where the traffic floor is
11 ms.

Every candidate mechanism inside that 86 ms has now been measured and is small: the scheduler's
cross-device drain (null), the peer's 47 device drains per pass (null), CUDA graph churn (0.03 ms per
token), full graph re-serialization (19 per pass, ~2 to 5 %), expert matvec bandwidth (85 % of
achievable) and the big dense projections (205 to 220 GB/s of 232). What is left is the shape of the
work: roughly 100 subgraph handoffs and 98 collectives per pass, each a serialized cross-host step of a
few hundred microseconds. The reference does the same arithmetic as a single captured graph per step
with its collectives inside it, which is a chain of one launch rather than a chain of a hundred.

That reading is supported by a comparison inside this repo rather than across engines: the single-Spark
`UD-Q2_K_XL` arm reads about 40 % fewer bytes per token than the 4-bit pair and is only about 10 %
faster (40.0 against 36 at c1). If bytes set the pace, the smaller quant would be far ahead; instead
both are dominated by the per-pass chain, which a smaller quant does not shorten.

So the remaining lever is not a knob and not a kernel: it is running a step as one graph per node with
the collectives inside it, which is the vLLM design and a rewrite of how the RPC split schedules work,
not a patch. Everything measured here says that closes the gap, and nothing available in this
configuration closes it in the small.

--- 2026-09-14, the GPUs are not idle, so the chain reading above is not supported ---

The section above reads the fixed cost of a pass as a chain of cross-host steps that leave the GPUs
waiting. That was an inference from a run of null results, not a measurement, and the measurement does
not back it.

`nvidia-smi dmon -s u` at 1 Hz over a three-rep c1 run:

| node | sm% through the decode window |
|---|---|
| client (spark1) | 79 - 95 % |
| peer (spark2) | 0 % throughout |

The peer reading is wrong. Its own counters show it executing about half of the ~100 subgraph
submissions per pass, and its power draw over the same window is 44.3 W mean (46.7 W max) against
13.5 W idle. Sampled the same way at about 3 Hz, the client's is 44.5 W mean (49.5 W max) against
14.3 W idle. Both GPUs are therefore working, at the same level, concurrently, which is what a
tensor-parallel split should look like. `dmon`'s sm% cannot be used on this pair: it reports zero on
at least one node while that node is demonstrably executing graphs.

What that leaves is a different target than the one the section above names. The pass is work-bound on
both nodes, and the work is small-batch and memory-latency bound rather than bandwidth bound. The
kernel profile already has the shape of it: the same dense ops run at 79 GB/s at one token per pass and
165 GB/s at five, against the 205 to 220 GB/s the large projections reach and the 232 GB/s this pair
reaches at a five-token batch. That is a kernel and batch-shape problem, not a coordination one, and it
is also why every coordination change measured here came out null: the scheduler drain, the 47 device
syncs per pass, the CUDA graph churn, the 19 full serializations per pass, and the two changes that did
land all move things that are not the bottleneck.

Unverified: the 40 to 50 % efficiency this implies is inferred from the op profile and the byte
accounting rather than measured end to end, and power draw cannot separate memory-stall time from
useful work. What is measured is that both nodes' GPUs work through the pass, at equal and roughly
three times their idle draw.

--- 2026-09-14, pinning the draft locally is closed by the scheduler in both forms ---

The draft costs 20.6 ms of every 131 ms pass and contributes roughly 30 of the ~100 subgraph handoffs,
so running it entirely on the client node is the obvious way to shorten the chain. Both ways of asking
for that abort in `ggml_backend_sched_backend_id_from_cur`, and both are pre-allocated-buffer
constraints rather than RPC problems:

- `-devd CUDA0` (draft device list narrowed): `pre-allocated tensor (output.weight) in a buffer
  (Meta()) that cannot run the operation (NONE)`, because tensor parallel with a full-output drafter
  sets `output_replicated` (common/common.cpp:1299) and a one-device draft context has no backend that
  can run that buffer.
- `-otd 'blk\..*=CUDA0'` (draft device list unchanged, its block tensors overridden to CUDA0):
  `pre-allocated tensor (blk.0.attn_q_b.weight) in a buffer (CUDA0) that cannot run the operation
  (NONE)`, the mirror image, with the tensor on one device and the draft context spanning two.

So the draft's handoffs cannot be removed by configuration, and short of changing how the split planner
and the scheduler agree on pre-allocated buffers, this lead is closed.

--- 2026-09-14, why the chain cannot be shortened by configuration: the copies are synchronous ---

Every A/B this work ran on the client's or the peer's per-request path came out null, and this is the
code path that explains it. When a split's input lives on one device and is consumed on another,
`ggml_backend_sched_compute_splits` calls `ggml_backend_tensor_copy(input, input_cpy)`
(`ggml/src/ggml-backend.cpp:1681` and `:1789`). For a source and destination that are both device
buffers on different backends, that function falls through (`ggml-backend.cpp:488-499`):
`ggml_backend_buffer_copy_tensor` returns false for CUDA to RPC, because the RPC backend's `cpy_tensor`
requires both tensors on the same server, so the copy ends in `ggml_backend_tensor_get` followed by a
set, that is, device to host to device.

`ggml_backend_tensor_get` on CUDA is a synchronous device-to-host copy, so it drains the local CUDA
stream, and the client's host then hands the bytes to the RPC backend, which is the non-blocking half
(`set_tensor_async`). The peer's counters put 47 of these per pass, which is the tensor-parallel
handoff, one per one or two subgraphs.

That is the mechanism behind the earlier client profile, which found the client's CPU spinning in
`cudaStreamSynchronize` while the GPUs were demonstrably busy (44 W each against 14 W idle). It is not
the scheduler's cross-backend drain, which was measured null, and it is not the peer's request path,
which was measured null. It is the client draining its own stream to stage each handoff through host
memory.

The two ways this can be fixed, both code rather than configuration, and both larger than a slice:
fuse the staging into a single async copy (`ggml_backend_tensor_copy_async` exists at
`ggml-backend.cpp:511` and the RPC backend already implements `set_tensor_async` and
`get_tensor_async`, so the pieces are there), or give the RPC backend a direct device-to-device path
for the handoff. Either way this is where the ~100-handoff chain and its exposure live, and it is the
first thing to attack rather than another configuration arm.

--- 2026-09-14, the host staging costs nothing either: 47 copies per pass removed for free ---

The section above names the staging copies as where the chain lives. Measured by removing them: the
host-staged cross-backend fallback in `ggml_backend_tensor_copy` (`ggml-backend.cpp:499-508`) gated on
`GGML_NO_STAGE_COPY`, which skips the device-to-host read and the set entirely, so the destination
keeps stale data and only the timing means anything (same method as the no-op allreduce test).

| c1, three reps | median | range | spread |
|---|---|---|---|
| baseline, staging intact | 40.4 (two runs) | 39.0 - 41.1 | 3 - 5 % |
| `GGML_NO_STAGE_COPY=1` | 39.4 | 37.5 - 41.8 | 11.1 % |

So removing all 47 of them changes nothing, and if anything the run is slower inside its own larger
spread. The staging is not exposed time either, which removes the last mechanism this work had for the
per-pass chain: the scheduler's cross-device drain (null), the 47 device drains on the peer (null), the
peer's request path (null), the collectives (9 ms of 125 ms by the no-op test), CUDA graph churn
(0.03 ms per token), graph re-serialization (2 to 5 %), and now the copies (null).

What is left, stated plainly: both GPUs work through the pass at 44 W each against 14 W idle, the
kernels are near this part's memory system when timed alone, and the pass still costs 125 ms where its
weight traffic floor is about 54 ms across the pair. Nothing measured removes the difference, so either
the kernels run much slower in situ than the offline replay shows (it is L2-warm and only times one
occurrence of each signature), or the pass contains work this accounting does not name. The offline
budget's own caveat points the same way: its 42.7 ms is 3x under the real pass for exactly those two
reasons.

--- 2026-09-14, the peer's subgraphs are captured, so its launches are cheap: closed from its own log ---

The remaining candidate for the unexplained time in a pass was the peer's per-subgraph launch cost: if
its deserialized graphs were not CUDA-graph captured, each of its ~80 subgraphs per pass would pay ~120
individual kernel launches at a few microseconds each, which is 20 to 40 ms per pass. The peer logs at
debug level already, so no new run was needed. Counted in its log from the last measured session
(`GGML_NO_STAGE_COPY`, two slots):

    CUDA graph warmup complete:  1299
    CUDA Graph id ... reused:  37588
    CUDA graph warmup reset:     521

Around 470 passes in that session, so ~80 graph reuses per pass and one and a half warmups: the peer's
subgraphs are captured and replayed, and its launch cost is a graph launch each, not 120 kernel
launches. The client's side was counted the same way earlier (154408 reuses, 8875 resets).

That closes the last launch-side mechanism. What the accounting now looks like for a 125 ms pass: peer
request path 3.5 ms (44 us times 80), collectives ~9 ms, graph launches on both sides ~1.6 ms, the
offline kernel budget 42.7 ms (L2-warm, one graph launch per signature), copies null, scheduler drain
null, peer drains null. That is roughly 55 ms accounted for and 70 ms not, and the only reading that
fits every null at once is that the kernels take substantially longer in situ than the replay shows,
because in situ they are waiting on DRAM latency rather than bandwidth. It fits the requantise null as
well: at the same latency, fewer bytes per kernel costs the same.

If that reading is right, no configuration change reaches the gap, and the work is inside the kernels
that wait: the small-batch matvecs and the many small elementwise ops, where the offline profile already
shows 79 GB/s at one token per pass against 165 GB/s at five and 205 to 220 GB/s for the large
projections.

--- 2026-09-14, the 70 ms is not a kernel slowdown either ---

The reading above (kernels slower in situ because they wait on DRAM latency) is weakened by a
measurement already in the profile: the lm head op is a single q8_0 matmul reading 552 MB, and the
offline replay times it at 2421.6 us, which is 218 GB/s. A 552 MB tensor cannot be L2-resident, so that
is a real streaming rate at 94 % of what the pair reaches, and it says the kernels can pull from DRAM
near peak when the tensor is large. Large tensors are what the dense family is made of.

For the small ops the replay's own numbers are small: the whole elementwise and normalisation set
(CONCAT, ADD, MUL, RMS_NORM, SUM_ROWS and the rest, about 1900 nodes) sums to roughly 4 ms of the
42.7 ms budget. To account for 70 ms they would have to be about twenty times slower in situ, which no
measurement suggests.

So the honest position after four turns on this goal: every mechanism this work can name is measured
and closed (scheduler drain, peer device drains, staging copies, peer request path, graph churn,
re-serialization, collectives, server-side launches, expert-matvec bandwidth, the MMVQ table, 4-bit KV,
fusion ceiling, and the requantise), the GPUs are demonstrably working through a pass, and the pass is
125 ms against a weight-traffic floor near 54 ms with about 70 ms that this accounting cannot name.

What would resolve it is in-situ per-kernel time on the client during a decode, which needs either a
profiler that this pair does not permit (perf and ptrace are denied, nsys came out 1.5 GB) or an
in-tree timer patch around each backend's graph compute, which is the one instrument not yet built.
That is the next thing to build, not another configuration arm.

--- 2026-09-14, in-situ timing: the scheduler owns 44 ms of a 111 ms pass, and 66 ms is outside it ---

The instrument this work was missing, built as a temporary env-gated patch (`GGML_SCHED_PROF=1`) around
`ggml_backend_sched_compute_splits` and the meta backend's allreduce, then reverted. One c1 arm at the
reference protocol, `-np 2`, 40.4 tok/s, 4.52 accepted tokens per pass, 229 passes, 1175 splits:

| stage, per pass | ms |
|---|---|
| cross-backend drain at the top of the split loop | 0.0 |
| input copy loop, including the syncs before expert copies | 6.6 |
| dispatch, `ggml_backend_graph_compute_async` for local and RPC splits | 37.5 |
| of which the NCCL allreduce | 20.8 |
| scheduler subtotal | 44.2 |
| outside `compute_splits` | 66.5 |
| pass total | 110.7 |

Two things change the picture. The drain is exactly zero, so there is no cross-backend stall at the

The larger finding is that 60 % of the pass, 66.5 ms, is outside the scheduler altogether: graph
construction or reuse, the speculative orchestration, sampling, and any GPU wait after the scheduler
returns. All three scheduler buckets are waits rather than work (a blocking collective, a blocking peer
response, and a synchronize before the copies), so the client's host thread is blocked, not spinning,
which is consistent with the earlier CPU sample that read as spinning.

orchestration, sampling and residual. That work is in flight.

Same instrument, now on the caller side (client), one c1 arm, 27.06 ms per token, 4.52 accepted, so
about 122 ms per pass, 237 passes in the window:

|---|---|---|
| graph build and reserve (host) | 3.34 | 2.7 % |
| of which reused | 0.00 | n=219 |
| of which rebuilt | 3.30 | n=487 |
| speculative orchestration | 23.11 | 18.9 % |

| explicit synchronization | 9.64 | 7.9 % |

Caveats the run carries: the window spans gates, warm and timed arms so the residual is not the timed
arm alone, and `llama_context::synchronize` also catches the sampler's and the draft's syncs, so the
buckets overlap slightly and their sum is a mild overcount. The residual also contains the scheduler's

Two new, actionable items come out of it.

The collectives are the largest single named target in the pass: 95 allreduces per pass at 218 us each
is 20.8 ms, which is 17 % of the pass and 2.3x the old no-op-allreduce estimate. The instrumented
bucket attributes them precisely because the peer counts them.

And the client rebuilds its graph on 487 of 706 passes, never reuses it in 219, and pays 3.3 ms of host
time for each rebuild. Those rebuilds are the draft's KV inject decode, whose token count varies with
how many tokens were accepted, and a rebuild is what takes the full-serialization RPC path: the peer
counters put 19 `graph_compute` against 80 `graph_recompute` per pass, and the draft's subgraph count is
about that size. So one variable-shaped decode per pass costs a host rebuild, a full graph
serialization, and a peer-side graph rebuild, every pass.

That is the first concrete target this work has found that is both small enough to attack and large
enough to matter: the draft's inject path, not the target model's.

--- 2026-09-14, NCCL protocol and channel controls make it slower, not faster ---

The collectives are the largest named bucket in a pass: 95 allreduces at about 218 us each, 20.8 ms,
which for a two-rank collective of roughly 100 kB is latency rather than bandwidth. Standard NCCL
controls were never tried here, so an A/B was run on the same arm, c1 at the reference protocol, three
reps, both nodes carrying the environment:

| arm | c1 median | range | spread | gates |
|---|---|---|---|---|
| A, only the two required variables | 41.1 | 41.0 - 41.6 | 1.5 % | pass |
| B, plus NCCL_PROTO=LL, NCCL_ALGO=RING, channels pinned to 1, 128 threads | 37.2 | 36.6 - 40.3 | 9.9 % | pass |

B is 9.5 % slower and the ranges do not overlap, so the controls cost throughput rather than helping the
latency-bound collective. No NCCL warnings in either arm, and the gates are identical, so quality is
untouched. Closed.

The same run re-measured the baseline at 41.1 (41.0 - 41.6), the tightest and highest c1 figure recorded
for this arm, against the 40.4 in the record and the 40.9 for the all-4-bit build. Read 41 as the
baseline.

--- 2026-09-14, the graph rebuild churn attributed and closed: alternating draft shapes, prize 5 % ---

Instrumented attribution, one run at the reference protocol, counts are process totals:

| decode site | calls | rebuilt | reused | rows per decode |
|---|---|---|---|---|
| target verify | 466 | 30 | 436 | min 1, max 19, avg 5.9 |
| draft block propose | 456 | 456 | 0 | always 5 |
| draft KV inject | 465 | 462 | 3 | min 1, max 19, avg 5.9 |

The hypothesis is partly refuted. The inject is not solely to blame: the draft's block propose is a
constant five rows and still rebuilds on every one of its 456 calls, because the two draft decodes
alternate between two shapes, inject about six rows against block five, and graph reuse requires an
identical token count. Every alternation rebuilds both, 918 of the draft's 921 decodes.

No safe fix exists, which is the useful part. Equalising the shapes means padding the block to six rows,
which writes a draft KV entry at a position the target never verified and changes the candidate count,
or trimming the inject to five, which drops a verified position from the draft KV. Both change what the
drafter sees, so both are out. There is no fixed-size draft window in this tree that would make the
inject match the block; the inject's size is set by the target verify batch, not by a tunable.

And the prize is small: 949 rebuilds at about 1.6 ms each is 1.5 s over a 29 s window, about 5 % of the
pass, so even a safe fix of this kind would not move the arm by more than a few percent. Closed, with no
patch made and the second load not spent.

Baseline re-measured in the same run at 37.8 tok/s median (37.3 - 41.7), gates unchanged, mean accepted
length 4.52 identical to before.

--- 2026-09-14, why the collectives cannot be replicated away: the plan makes them, and it already uses MIRRORED ---

Read-only study of whether the ~95 allreduces and ~100 subgraph boundaries per pass can be removed by
replicating small tensors or pinning some to one device. Both are no-go, and the reason is worth
recording because it closes the last idea for shrinking the chain from the plan side.

Where the boundaries come from: `n_subgraphs` increments only at nodes whose split axis is PARTIAL
(`ggml-backend-meta.cpp:2204`), and one allreduce runs per subgraph except the last (`:2447`). PARTIAL
arises from row-parallel linears, a MUL_MAT whose weight and activation are both axis 0
(`:591-593`). The dense q/k/v projections are axis 1 (`src/llama-model.cpp:513-527`) and produce no
collective. The row-parallel set, and therefore the collective set, is attn_output
(`src/llama-model.cpp:532`), ffn_down (`:571`) and ffn_down_exps (`:579`). So replicating the small
dense tensors removes nothing: they are column-parallel and already cheap of collectives. The count is
what this split plan requires, which is the same count any tensor-parallel plan has.

Replication is not a new axis to add: MIRRORED is already the general axis and the fallback for
unrecognised tensors (`src/llama-model.cpp:596`), with explicit cases for biases, norms and caches.
`output_replicated` is the only named-list-like mechanism, a single bool (`common/common.cpp:1299`,
`src/llama-model.cpp:584, 594, 1200`). Extending it to a named list is 40 to 70 lines of plumbing, but
the risk sits in the meta backend's propagation asserts (`ggml-backend-meta.cpp:557, 605, 755-779`), and
by the paragraph above it would not remove the collectives that matter.

Pinning a tensor to one device is structurally outside the design. In tensor mode the scheduler's
backends are `[meta, CPU]`, never the raw CUDA device. `ggml_backend_sched_backend_id_from_cur`
(`ggml-backend.cpp:921`) resolves a pre-allocated tensor through
`ggml_backend_sched_backend_from_buffer` (`:889`), which needs a backend whose
`supports_buft` and `supports_op` both pass (`:897-898`); the meta device accepts a buffer only if its
device is a meta device with an identical, same-order simple-device vector
(`ggml-backend-meta.cpp:161-178`). A raw CUDA0 buffer, which is what both `-otd` and `-devd` produce,
has no such owner, hence the abort at `:941`. Accepting it needs the meta device to claim foreign
buffers and copy, or the scheduler to carry simple devices, either of which is a redesign rather than a
patch.

Conclusion: the chain is irreducible from the planning side. What the reference does differently is not
fewer collectives, it is executing the step as one graph per node with the collectives inside it, so
there is no host round trip per boundary. That is the execution-shape project, and nothing smaller
reaches it.

--- 2026-09-14, the KV cache is not a cross-device traffic source: placement measured ---

Asked whether the scheduler needs awareness of where the KV cache and certain weights live. From the
startup log of the tensor-parallel arm (`srv-dev.log`, the `-devd` attempt, which had the main model
loaded in tensor mode before it aborted on the draft):

    167 layers assigned dev = Meta()          (all of the main model)
    3 layers assigned dev = CUDA0             (the draft context's caches)
    Meta() KV buffer sizes: 172.00, 42.00, 40.00, 10.50 MiB
    CUDA0 KV buffer size: 24.00 MiB           (draft)

So the main model's cache is expressed as a per-layer device assignment, lands in the two-device meta
buffer, and totals about 265 MiB. At the context lengths the benchmark uses it is not a traffic source,
which matches the boundary analysis: the 95 collectives per pass come from the row-parallel linear
projections (`attn_output`, `ffn_down`, `ffn_down_exps`), not from attention or the cache.

The awareness that is missing is of a different kind, and it is the one this work kept running into: a
cost model for boundaries, so the planner knows a split costs an exposed collective and a submission;
and a way to say that a sub-model lives on one device while the model spans two, which is what pinning
the draft needs and what aborts today in `ggml_backend_sched_backend_from_buffer`. The draft's own
forward passes are 23 ms of a 122 ms pass, so that second gap is the first slice of the execution-shape
project rather than an optimisation of it.

--- 2026-09-14, why the draft cannot be pinned without giving it its own lm_head ---

Both pinning routes abort for one shared reason, and the reason has a named fix.

The DSpark draft gguf has no `output.weight` of its own (`common/speculative.cpp:2361-2362`), so its
graph binds the target's lm_head directly (`src/models/dflash.cpp:989-997` and `:780-791`, with the same
fallback for the token embedding at `:893-897`). That is why `output_replicated` is set
(`common/common.cpp:1299-1302`, `src/models/dflash.cpp:155-157`), and under that flag the target's
`output.weight` is MIRRORED (`src/llama-model.cpp:584-586`) inside the target's two-device Meta buffer.

`-devd CUDA0` already does the right thing on the draft side: it sets the draft's device list
(`common/arg.cpp:4204`) and drops the meta wrapper for a single device
(`common/speculative.cpp:2522-2528`), so the draft's scheduler becomes `[CUDA0, CPU]`. It then has to
claim the target's Meta buffer, and `ggml_backend_sched_backend_from_buffer`
(`ggml/src/ggml-backend.cpp:889-898`) only returns a backend whose `supports_buft` passes; a Meta buft is
claimed only by a meta device with an identical same-order simple-device vector
(`ggml/src/ggml-backend-meta.cpp:161-178`). It returns -1 and the abort fires at `:941`.

The two shortcut rescues are out. Granting the single-device scheduler a Meta buffer would run the
target's meta split-state code over the draft graph, whose userdata is bound to the target model
(`src/llama.cpp:176-179`), asserting on unknown names (`ggml-backend-meta.cpp:605`) and producing a wrong
split. Handing the draft the meta buffer's per-device slice is unsafe because slices live in a
compute-scoped container reset on every graph rebuild (`ggml-backend-meta.cpp:2010-2016`), so the
reference would dangle. `-otd` does not meet the goal either, since unmatched draft tensors and the
shared head stay on the meta device.

So the fix is a real replica: give the draft its own copy of the shared lm_head in a buffer its single
device can run, copied once at load, gated on the draft having one device so the multi-device path is
unchanged. The prize is the one this goal needs, 23 ms of a 122 ms pass plus about 30 of the ~100
handoffs, so it is worth 15 to 20 %. That implementation is in flight.

--- 2026-09-15, the fused HC ops are active, fusion has no big chain left, and the per-op reading stands untested ---

Two facts, both cheap, and one correction.

The DeepSeek V4 hyper-connection fused kernels are selected in the configuration we measure. At `-lv 4`
the log carries `resolve_fused_ops: fused DeepSeek V4 HC pre/comb/post enabled`. They were invisible
before because `common/log.cpp:532` maps `GGML_LOG_LEVEL_INFO` to `LOG_LEVEL_TRACE` (4) while the server

`sched_reserve`'s "reserving", is filtered at the default verbosity. Nothing was disabled; the logs were
just quiet. Use `-lv 4` when a llama-library INFO line matters.

And the fusion candidate was an order of magnitude too big in the earlier study: `build_hc_mean` runs
only when `embeddings_layer_inp[il]` is set (`src/models/deepseek4.cpp:1240`) plus once for the head

fusing it could not clear the stated 2 % falsification bar and was not implemented; the change would
have been roughly 200 lines across nine files for an uninformative result.

Consequence: because the HC kernels are selected, the unfused HC chains that motivated the study,
including the sinkhorn row reductions, are not executing, so the premise of a large fusible chain in
this graph is wrong. The per-operation reading is therefore still untested rather than supported, and
what is left is that it is the last explanation standing by elimination: the byte count is shown not to
bind (requantise, 1 % for 28 % fewer bytes), the handoffs and collectives are shown not to bind (draft
pinned single-device, half the handoffs and 54 % of the collectives, no change), the kernel bandwidths
are near the part's reach when measured alone, and the coordination mechanisms are all null.

To settle it needs a lever that removes a double-digit share of the roughly 5200 operations in a pass,
and this graph no longer offers one that is already fused away.

--- 2026-09-15, queued: the CUDA graph warmup churn has a located cause ---

Graphs on beat graphs off by 5.5 % at eight slots (38.1 against 36.1 at c1) and are level with it at
two (40.4 and 40.8 on against 41.1 off, inside spread), so they stay on; the earlier reason for
leaving the churn alone was that it is unsafe to touch. The code says where it comes from, and it
does not look unsafe:

- `ggml/src/ggml-cuda/ggml-cuda.cu:2699`, the per-graph cache key is `cgraph->nodes[0]`, that is the
  pointer of the first node of whatever graph the backend is handed;
- `:4709` to `:4728`, warmup needs two consecutive calls on that key with no property change, and any
  later property change resets warmup to needing two more;
- `:2703` to `:2743`, "property change" includes every source tensor's *data pointer*
  (`node_src_data_ptrs`), not only shapes and types.

Under `-sm tensor` the meta backend hands the CUDA backend one subgraph per split, so a pass is
hundreds of separate `graph_compute` calls, each with its own first node and therefore its own cache
entry, and each needing its own two stable calls. The recorded run logged 8875 warmup resets against
9240 completions, which is the shape of that, not of one graph flipping.

Two candidate fixes, cheapest first: key the cache on the graph's structure rather than the first
node's address, and drop the source data pointer from the property comparison, since a reallocated
buffer with the same shape and type is what CUDA graph node updates exist for anyway. Both need the
two-slot and the eight-slot arms before they go in, and the eight-slot arm is where the 17 % is.

| SUM_ROWS | 105 | 0.2 |
| SCALE | 321 | 0.2 |
| SET_ROWS | 250 | 0.2 |
| **total** | **~3600** | **5.9** |

So the isolated work in the whole unfused remainder is 5.9 ms of a 114 ms pass. The estimate an hour
earlier put it at 12 to 24 ms by charging each node 5 to 10 us in situ; the difference between that and
5.9 ms is the per-node serialisation cost, which is what a fused kernel would remove, and it is bounded
above by the 5.9 ms if the fused kernels themselves are free. **Writing an elementwise fusion pattern is
therefore worth at most 5 % of a pass**, less than the 10 % the existing fusion already buys, where the
fusions that pay are the big ones (the MoE gate+up+GLU chain, the shared expert's, and the norm and rope
chains).

This closes fusion as a direction for this engine. The corrected sentence in `docs/targets.md` still
stands on the measured 10 %, but the 12 to 24 ms in the entry above should be read as an upper bound
that did not survive measurement.

--- 2026-09-15, both devices are half idle through a pass ---

`nvidia-smi` sampled at 200 ms on both nodes through one c1 rep, current best configuration (two slots,
tensor parallel over RPC, DSpark, fusion on):

|---|---|---|---|
| client | 49.9 % | 35.4 W | 2471 MHz |

101 samples each, one pass. The clocks are at their full value and the power is 33 to 35 W against the
~14 W idle this record measured earlier, so the devices are not throttled and not busier than this: they
are working about half the time.

That is the piece of evidence the last several entries were missing. It says the pass is not
kernel-bound: the isolated work of every op in the graph sums to 42.7 ms (matmuls) plus 5.9 ms
(elementwise and copies), and the pass is 114 to 120 ms with the devices half busy, so the device-side
occupancy is roughly 60 ms of a 114 ms pass and the other ~54 ms is waiting.

The waiting decomposes into three terms that are each already measured or bounded: the collectives, 21
to 23 ms, measured by removing them; the draft, 17 ms, during which the peer has nothing to do at all
because the draft is pinned to one device; and about 15 to 20 ms of per-subgraph round trips, one per
split, 106 of them, where the client's dispatch is on the critical path of the peer's next subgraph.

Everything follows from that: kernel work cannot pay, which is why the MMVQ table, the warp counts and
now the fusion extension are all 2 to 5 % or null; the reference pays 0.2 ms a layer for its collectives
against our 0.49, because its two ranks are in one process and there is no round trip between them; and
the only two levers left of any size are making the draft overlap with something and taking the round
trips out of the per-layer path, which means a collective design that does not need the peer to be told
per layer, which is what PR #26610's dedicated comm channel is for.

--- 2026-09-15, the half-idle time is between kernels, which corrects the fusion conclusion ---

`ggml_backend_cuda_graph_compute` now brackets each subgraph with events (`GGML_CUDA_SUB_PROF=1`), so
the client's stream occupancy can be compared with the device's kernel occupancy. One c1 rep, graphs on:

    windows=512 total=14780.0ms mean=28.9ms worst=14073.4ms

The worst entry is an outlier of the same shape the allreduce timer produced, and the instrument is
unreliable for that reason, but the subtraction is still usable: 14780.0 minus 14073.4 over the other

Against that, `nvidia-smi` sampled through the same configuration reports a kernel resident only half
the time (49.9 % client, 51.4 % peer, 33 to 35 W, clocks at full). Both can be true only one way: the
device is idle by half, and it is idle *inside* the subgraphs, between the kernels of a chain. A pass
runs on the order of 5200 kernels; half of 114 ms spread over them is about 11 us of start and drain
per kernel.

**That corrects yesterday's fusion conclusion, which measured the wrong quantity.** The entry above says
extending fusion is worth at most 5.9 ms because that is the isolated work of the unfused families. If a
kernel costs 11 us to start regardless of what it does, the value of removing it is 11 us, not its work,
and the elementwise and copy families are 3600 kernels: fusing them down to a few hundred is worth on
the order of 20 ms, 17 % of a pass, which is the largest identified term in the engine and larger than
the collectives. The same arithmetic explains why the existing fusion, which merges a few hundred nodes,
is worth the measured 10 %: 15 ms over 114 ms.

What this does not say is that such a fusion is easy. It says the reason to write one is kernel count,
the earlier reason to not write one was work, and the kernel count is the one that matches the two
independent occupancy measurements.

--- 2026-09-15, the kernel-gap arithmetic does not survive the kernel census ---

--- 2026-09-15, how the MoE matvec is laid out, and why the rewrite case is weaker than it looked ---

Reading the call site settles the indexing. In `ggml_cuda_mul_mat_vec_q` (`ggml/src/ggml-cuda/mmvq.cu`
around :1535) the MUL_MAT_ID layout is `ncols_dst = ne2` and `nchannels_dst = ne1`, which for a MoE
output of `[n_embd, n_expert_used, n_tokens]` means the **grid's y dimension is the k-slot**, not the
used experts, and the block's y dimension, `ncols_dst`, is the tokens. In `mul_mat_vec_q_moe` each warp
takes `channel_x = ids[k_slot + token*ids_stride]`, so the six warps of a block are six tokens' k-th
expert, each warp reading that expert's rows for its own token.

Two consequences.

**The redundancy is real but it is L2-level.** Of the 36 (token, slot) pairs a call carries, about 20
distinct experts are used, so the weights are *issued* about 1.8 times where they need to be read once.
DRAM still sees the distinct 88 MB per node a call, because the repeats land in L2. At the profiler's
586 us that is 150 GB/s of DRAM, and the issued traffic is nearer 160 MB. So the rewrite the previous
entry proposed, giving a block an expert and several tokens, removes issued traffic and L2 pressure, not
DRAM traffic, and it is only worth doing if L2 pressure is what limits the kernel. Nothing here shows
that it is.

**The 150 GB/s is not special to the MoE.** `mul_mat_vec_q<Q8_0,6>` carries the dense family at 24.3 ms
a pass for roughly the same per-node bytes, which is also about 150 to 165 GB/s, while a single large
op in situ, `node_19` at 35 MB, was measured at 231 GB/s earlier in this record. So the small shapes as
a class sit at 55 to 60 % of the 273 GB/s peak and the large ones at 85 %, and the MoE is the biggest
member of the slow class rather than a separate problem. What separates them is not size: the MoE's call
is 88 MB against `node_19`'s 35 MB.

**A correction to an earlier entry.** The `us per call by distinct experts` table, 76 us at six experts
and 218 us at thirty-six, is host-side: those events bracket the dispatch function, which returns as
soon as the kernel is enqueued. Against the profiler's 586 us of kernel time for the same call, that
table measures the wrong side of the launch and should not be read as kernel cost.

So the question the next kernel attempt has to answer first is what makes a 6-token, 20-expert matvec
run at 150 GB/s when a 35 MB dense matvec runs at 231, and neither block shape nor issued traffic
answers it.

--- 2026-09-15, the MoE is at the memory system for the traffic it issues, and 40 % of that is redundant ---

Joining the fit of the previous entry to the profiler's kernel times closes the arithmetic, and it does
so in a way that names a fix.

The kernel issues one expert row-read per (token, k-slot) pair. `ncols_dst` is the token count and the
grid's y dimension is the k-slot, so a call carries `tokens * k` pairs, which for this model is 36, while
the distinct experts behind them are about 20. Per node a call therefore reads

    36 slots x 2 rows x 4096 K x 0.53 B x 2 matrices / 2 for the split  =  160 MB issued
    20 experts x 2 matrices x 2.2 MB                                   =   89 MB distinct

and the profiler's 586 us for that call is **273 GB/s of issued traffic**, which is this part's peak.
The same fit across a pass: the MoE's 40.5 ms at 273 GB/s is 11 GB of issued traffic where the distinct
data is about 6.5 GB. So the MoE is not at 55 % of the memory system as the previous entry read it; it
is at the limit, and **40 % of what it moves is the same expert rows read again for other slots**.

That is the fix: one row read per expert per row-block, applied to every token that selected that
expert, which takes the MoE from 40.5 ms to about 24 ms a pass and the pass by roughly 16 ms, 14 %.

The pieces to do it exist and neither is on the path today:

- `ggml_cuda_launch_mm_ids_helper` (`ggml/src/ggml-cuda/mmid.cu:133`) already builds `expert_bounds`
  plus the compacted column maps on the device, with no host synchronisation. It is used by the MMQ
  path at `ggml/src/ggml-cuda/mmf.cu:87`.
- the sorted, host-side compaction in `ggml_cuda_mul_mat_id` (`ggml/src/ggml-cuda/ggml-cuda.cu:2287`)
  does the same job with a `cudaMemcpyAsync` plus `cudaStreamSynchronize`, and says in its own comment
  that it must not be reached while recording a graph. So the grouped shape of the work already exists
  in this file, on the path this device does not take.

What has to be written is a grouped kernel in `mmvq.cu`: same warp structure as the existing one, but
with the grid's y dimension over used experts and each block reading its expert's `c_rows_per_block`
rows once for the `[expert_bounds[e], expert_bounds[e+1])` tokens, plus the dispatch in
`ggml_cuda_mul_mat_vec_q` to launch the helper and pass the bounds. That is a few hundred lines and it
is the next slice; it is also the only change in this record with an arithmetic case rather than a
measured null.

--- 2026-09-15, the redundancy figure, and the split axis does not change the case ---

Two corrections to keep the arithmetic above honest.

**How much is redundant depends on which histogram read is used.** The counter's own 1000-call mean was
23.9 distinct experts for 38.5 slots, which is 40 % redundant; the decode-only reading, 16.25 for the
921 calls that are not the prompt chunk, is 55 % redundant. Both are in
`GGML_MMID_STATS distinct experts histogram` above and the entry used the first. The fix is worth a MoE
of 40.5 ms becoming somewhere between 24 and 18 ms, so 16 to 22 ms a pass, 14 to 19 %.

**The tensor-parallel split axis does not matter to the figure.** Halving the expert along K leaves each
warp reading two rows of half the K, halving the rows leaves it reading one row of all K; either way a
warp moves the same bytes, the call issues about 160 MB, and 160 MB in the profiler's 586 us is
273 GB/s, the part's peak. That is worth stating because the split axis for the 3D expert tensor is one
of the few facts about this configuration that is still not read off a log.

--- 2026-09-15, how to develop the grouped MoE kernel without spending loads on it ---

The next slice is a few hundred lines in `mmvq.cu` plus dispatch, and the thing that makes it tractable
is that it does not need the rig to be debugged: `test-backend-ops test -o MUL_MAT_ID` runs the case
against the CPU backend and catches a wrong index or stride in seconds, with no model load. The order
that follows is: write the kernel and the dispatch, build on spark1, run the backend-ops case until it
is clean, and only then take a load to measure it. Every kernel experiment in this record that went
straight to a load spent 25 minutes per attempt.

The design as far as it is settled, so the next session does not re-derive it:

- the grouped shape needs the tokens per expert, which `ggml_cuda_launch_mm_ids_helper`
  (`mmid.cu:133`) already builds on the device, no host sync, `expert_bounds` plus a compact map;
- `ids_src1[compact]` decodes to `token*sis1 + slot`, with `sis1 = src1->nb[2]/src1->nb[1]`, so a kernel
  given the bounds can find both the tokens and their activations;
- the launch cannot take a data-dependent grid, because CUDA graphs capture the launch parameters, so
  the used-expert count cannot come from the device. A fixed `grid.y = n_expert_used` with each block
  scanning the 256-entry `expert_bounds` for its share of the populated experts keeps 6144 blocks where
  the current kernel has 6144 and needs no host round trip;
- the weight read is only shared if a *thread* holds one accumulator per token, which is the standard
  MMVQ structure (`tmp[ncols_dst][rows_per_block]`, one K loop). A block of warps each keeping one
  token's accumulator does not share the read and does not save anything. This is the trap in the
  obvious version of this change.

The save to expect is the 40 to 55 % redundancy, so a MoE of 18 to 24 ms instead of 40.5, and 14 to 19 %
of a pass. Nothing in this record has a larger measured case, and I have not started it.

--- 2026-09-15, the MoE redundancy looks like reuse distance, and the grid axes are the knob ---

Working the grouped-kernel design down to what actually causes the redundant DRAM reads gives a smaller
change than a new kernel. The reads are not shared because the *issue order* puts them far apart, not
because a block cannot hold two tokens' accumulators.

`mul_mat_vec_q_moe_launch` launches `dim3 block_nums(nblocks_rows, nchannels_dst)`, that is rows on x
and the six k-slots on y, and CUDA issues blocks x-fastest. So the blocks in flight together are
hundreds of consecutive row blocks of *one* k-slot, which between them read distinct rows and reuse
nothing, while the blocks for the other five slots of the same row range are 1024 blocks later, by which
time those rows are gone. What has to be reread per row range is small: the distinct rows behind 36
(token, slot) pairs and 20 experts are some tens of kilobytes a node, which any L2 holds. Swapping the
two axes puts the six slot blocks of one row range next to each other in the issue order, so the second
to sixth reads of an expert hit cache instead of DRAM.

That is the whole change: `dim3 block_nums(nchannels_dst, nblocks_rows)` with `channel_dst = blockIdx.x`
and `row0 = c_rows_per_block*blockIdx.y`, behind `GGML_MMOE_SWAP_PATH` so both orderings fit in one
server.

**Verified before measuring**, which is the part worth keeping: `test-backend-ops test -o MUL_MAT_ID`
runs 913 cases against the CPU backend in seconds with no model load, and both orderings pass it,
`913/913` with the swap on and off. That is the loop the kernel work in this file should have been
using; every kernel experiment before this one went straight to a 25-minute load.

Prediction, from the redundancy measured at 40 to 55 % of the MoE's issued traffic: the MoE's 40.5 ms a
pass becomes 23 to 28 ms and the pass falls by 10 to 14 %. The measurement is running.

--- 2026-09-15, the grid swap is a regression, and it kills the grouped-kernel project with it ---

The change verified offline an hour ago is a loss on the rig. Alternating arms inside one load, two reps
an arm, same server:

| round | as before | axes swapped |
|---|---|---|
| 1 | 41.2 | 39.9 |
| 2 | 36.0 | 31.1 |
| 3 | 38.3 | 32.1 |

The swapped arm is slower every round, by 3, 14 and 16 %. The first A/B/A had it at 34.8 / 41.3 / 31.5,
which read as a 17 % win with a tight spread on the swapped arm, and that was drift: the same
configuration moved 41.2 to 31.1 across rounds in the alternating run, so a single fast window decided
the earlier result. This is the clearest instance in the record of why the switching has to be
alternating and not bracketed.

**Why it is slower also settles what the redundancy was doing.** Swapping the axes puts the six k-slot
blocks of one row range next to each other, which was supposed to turn the second to sixth reads of an
expert into cache hits. That it does not help says the redundant reads were already being served from
cache, and the reason is the L2's size: the reuse distance in the original ordering is 1024 blocks of
26 KB, about 27 MB, which a part of this class holds. What the swap does instead is make consecutive
blocks alternate between six rows ranges and their experts, which hurts DRAM locality, and that is what
shows up as the loss.

**So the MoE's DRAM traffic is the distinct data, not the issued data.** That reverses the arithmetic of
two entries above: 89 MB a call in the profiler's 586 us is **152 GB/s, 55 % of this part's peak**, and
the kernel is not at the memory system. The 1.8x redundancy is real but it costs L2 bandwidth and
nothing else, which is exactly why the fix aimed at it, including the grouped kernel this was a
cheap stand-in for, cannot pay. The grouped kernel should not be written.

What is left of that question is the one from before the swap: why a 6-token, 20-expert matvec reaches
152 GB/s where a 35 MB dense matvec reaches 231, and neither block shape, issue order, nor issued
traffic explains it. The MoE is 40.5 ms of a 106 ms kernel pass, so it is worth another attempt, but not
another one aimed at its traffic.

--- 2026-09-15, where this stands, what is closed, and what the bar would need ---

Twelve hours of this session, 68 turns, and the honest summary is this.

**The number.** Best c1 arm measured: 41.2 tok/s, alternating arms, two reps, gates passing. The
reference image on the same pair is 63.1. The ratio is 1.53 and it has been between 1.5 and 1.6 at every
concurrency level for the whole project.

**The pass.** 114 to 124 ms for 4.52 accepted tokens, with 106 ms of GPU kernel time in it and a kernel
resident 74 % of the time. MoE expert matvecs 40.5 ms, dense matvecs 24.3, NCCL allreduce kernels 13.4,
everything else about 28. Two devices, two nodes, tensor parallel over RPC, DSpark n_max 5, 4-bit
weights, f16 cache.

**Closed, each by measurement rather than by argument.**

- the collectives cost 21 to 23 ms a pass, measured by removing them on both ranks, and of that 13.4 ms
  is the allreduce kernels and about 8 ms the host and the waiting;
- the launch path is not the cost (null), the peer's dispatch latency is not the cost (prefetch null),
  and `GGML_CUDA_ALLREDUCE=internal` cannot supply an alternative because its pipeline is single-host;
- the draft is 17 ms, of which about 8 is its own head read at 1.06 GB bf16; it is not truncated
  (`p_min` defaults to 0) and it does not benefit from being split across devices;
- fusion: the existing patterns are worth 10 % (measured by switching them off) and the unfused
  remainder carries 5.9 ms of work a pass, so extending fusion has at most 5 % in it;
- the MoE's redundancy: 36 (token, k-slot) pairs behind about 20 experts means 1.8 times the distinct
  bytes are issued, but that traffic is absorbed by cache, proven by the grid reordering that would
  exploit it being a 3 to 16 % *regression*. The grouped kernel that would remove it cannot pay;
- the verify batch: eight tokens costs 26 % more op time for 2.4 % less acceptance, so n_max 5 is right
  and the ngram idea in the same family is closed with it;
- codegen is native `sm_121a`; the KV cache is better in f16 than at 4 bits; TurboQuant is KV-side and
  does not touch this pass; the MMQ path for MUL_MAT_ID does not exist on this device by design.

**Open, and larger than a session.** The MoE at 152 GB/s of distinct traffic where a single large dense
matvec reaches 231, with block shape, issue order and issued traffic all now excluded. The allreduce
kernel at 134 us for 24 KB, which is about four times what the message should cost and is most likely
the peer's arrival rather than NCCL, unmeasured on the peer's side. A transport that does not need the
peer told per layer, which is what PR #26610's dedicated channel is for.

**What the bar would need, honestly.** 74 ms a pass. The byte-bound work in a pass is about 59 ms at
the pair's measured rate, the collectives are 21 to 23 on top, and the draft 17 more, so no combination
of the levers in this record reaches it: they would have to *all* come back and then some. The
reference reaches 74 ms by having both ranks in one process with no per-layer round trip, and by a
drafter that accepts 4.92 tokens where ours takes 4.52. Beating it needs the engine's small-batch rate
raised by about half, which is a kernel campaign of the size this session could not finish, or a
different execution shape than a per-layer allreduce over a socket.

Wrote a two-rank NCCL microbenchmark (`.scratch/nccl-lat.cu`) at the message sizes this engine moves

A verified token is 4096 halves, so the allreduce tensor for six tokens is 48 kB, and **NCCL's round

Instrumented the peer's request loop per command (`GGML_AR_SRV_PROF=1`, printing every 2000 graph
dispatches because the RPC server has no signal handler for its destructors). One c1 rep, 113 passes:

| path | calls | total | us each |
|---|---|---|---|
| `RPC_CMD_GRAPH_RECOMPUTE` (uid cache hit) | 8050 | 229.7 ms | **28.5** |
| `RPC_CMD_GRAPH_COMPUTE` (full graph sent) | 1950 | 4978.4 ms | **2553** |

Ten thousand dispatches for 113 passes is 88.5 a pass, which matches the subgraph count, so this is the

Why it stalls the client rather than hiding: the client's RPC send is fire-and-forget, so the peer's

Why 17 rather than none: the cache keys on the graph's uid, and both the scheduler
(`ggml_backend_sched_split_graph`) and the meta backend (`ggml_backend-meta.cpp:2295`) hand out a fresh

cache does what it was told.

What to do about it is the work this entry hands over, and it is now the largest item in this record
after the MoE: either fewer subgraphs, or a peer-side cache that survives an address change for the
subgraphs that only move, or a spin of the loop that keeps the peer's host off the client's critical
path. None of those is a knob, and the first thing to try is printing which subgraphs miss and why,
which the client side can do with one more counter.

--- 2026-09-15, 95 % of the RPC cache misses are graphs the peer already has ---

Client-side diagnostic (`GGML_RPC_CACHE_DIAG=1`) over one c1 rep, 11,737 dispatches, classifying every

| bucket | calls | share |
|---|---|---|
| uid hit, peer already has it | 9381 | 79.9 % |
| same structure, same addresses | 396 | 3.4 % |
| **same structure, addresses moved** | **1843** | **15.7 %** |
| new structure | 117 | 1.0 % |

So 2,239 of the 2,356 misses are graphs whose structure the peer already holds, and 1,843 of those are
the interesting kind: same nodes, same shapes, different addresses. At the peer's 2.55 ms per full graph
that is 4.7 s of peer host time a rep that a smaller message would avoid, which is the 27 ms a pass this
record attached to the peer's host last entry. The 396 in the middle are trivially fixable and worth
1 %. The 1,843 need a message that carries new pointers instead of a whole graph.

**And they need one question answered first, which this entry does not answer.** The pointers the client
sends in a serialized graph are the *remote* addresses the peer gave it, so a client-side diagnostic
sees addresses moving without being able to say whose they are. If what moves is a buffer the peer
reallocates on its own side, then the client's cache entry is stale by right and no message from the
client can fix it, because the new value was never sent to the client. If what moves is a client-side
allocation that the peer reads, an update message is the fix and the traversal that builds the tensor
list already exists (`add_tensor`, which both sides can replay in the same order for the same
structure).

The cheap way to tell them apart is to print, for the moved cases, how many of the changed pointers
belong to tensors the client owns and how many to ones the RPC backend owns. That is another cycle, and
it is the right next step: an update path built on the wrong assumption about pointer ownership is
exactly the kind of change that produces wrong numbers rather than slow ones.

--- 2026-09-15, the pointer ownership, answered by reading ---

The open question in the entry above is answered by the code, so an update message is sound and does not
need a rig cycle to justify.

`ggml_backend_rpc_buffer_get_base` (`ggml/src/ggml-rpc/ggml-rpc.cpp:661`) asks the peer for the buffer's
base address once and caches it, and the *client's* graph allocator assigns every tensor its offset into
that base. So a tensor in a subgraph the peer runs has a `data` pointer that is **the peer's base plus a
client-chosen offset**, and when the diagnostic sees an address move, the new value is one the client
already knows. The peer does not re-plan: its server creates tensors from the serialized `rpc_tensor`
values and runs the graph with them verbatim, which is why the full message exists at all. Nothing on
the peer's side can move behind the client's back, and an update message is therefore faithful rather
than a guess.

The change that follows, for whoever takes it:

- a `RPC_CMD_GRAPH_UPDATE` message carrying device, uid, comm, post_compute, post_node, a tensor count,
  and then that many `uint64` pointers, using the two-part message shape `set_tensor` already uses;
- the client keys a map on the structural hash the diagnostic already computes (`struct_key`), and on a
  uid miss with a known structure whose old uid is still in its own cache, sends the update instead of
  the graph, adding the new uid to the cache so later passes hit it directly;
- the peer records the tensor order when it deserializes, so the update can assign the pointers by
  position, then runs the same tail as `graph_recompute`;
- the traversal order has to match `add_tensor`'s, which is deterministic for a fixed structure, and the
  update path must not re-register tensor ids.

Worth 1,843 of 11,737 dispatches a rep, 15.7 %, at 2.55 ms of peer host each against 28.5 us for the path
that already works, which is the 27 ms a pass this record attached to the peer's host two entries ago.
It is default-off in a switch, so the tree stays correct if it is wrong, and the gates are what says
whether it is.

- the update path pre-created every tensor in the message order so the order could be recorded, which
  meant `create_node` found each tensor already in `tensor_map` and returned at its first line. Sources
  and `view_src` are linked only in the code below that line (`ggml-rpc.cpp:2219`), so every node in
  every graph the peer built had null `src[]`, and the first kernel that dereferenced one took the
  process down with no message. The fix keeps upstream's traversal and resolves the order afterwards
  from the same `tensor_map` `create_node` fills, so nothing about graph construction changes.
- the update message re-used the entry under its **old** uid and the client cached the **new** one, so
  the next pass would have sent a recompute for a uid the peer had never been told about. That is a
  `return false`, which closes the connection. The message now carries both uids and the peer moves the
  entry to the new key (`extract` + re-key, not a copy: a stored graph's nodes live in the entry's own
  arena).

Neither bug is measurable from the client side, and neither showed up as an error: the first is a silent
segfault in the peer and the second is a hang. What would have caught them earlier is the peer's own
liveness as a gate, which the A/B script does not check, only its log. That is now the cheapest fix to
the harness: the pass conditions should include `pgrep -x ggml-rpc-server` on the peer at every poll.

--- 2026-09-15, a cold single launch per dense shape: the small ones are latency, not bandwidth ---

`tests/test-backend-ops perf -o MUL_MAT -p <shape>`, with the perf-only cases added for these shapes, and
`GGML_TEST_FLUSH_L2=1 GGML_TEST_N_RUNS=1` so the clock covers one launch reading its weights from DRAM
(the flush is completed and synchronized before the clock starts, or its 256 MB of writes land in the
timed region). Bytes are `m*k` at the type's block size, 34/32 for Q8_0 and 17/32 for MXFP4.

| shape | type | MB | us | GB/s |
|---|---|---|---|---|
| 129280 x 6 x 4096 (lm head) | q8_0 | 562 | 2566 | **219** |
| 16384 x 6 x 1024 (q_b half) | q8_0 | 17.8 | 148 | 120 |
| 4096 x 6 x 4096 (out_b half) | q8_0 | 17.8 | 152 | 117 |
| 2048 x 6 x 4096 (expert rows) | mxfp4 | 4.45 | 54.5 | 82 |
| 1024 x 6 x 4096 | mxfp4 | 2.23 | 34.7 | 64 |

Marginal bandwidth between the two large ones is 222 GB/s, so the ceiling is real and reachable; what the
small shapes pay is a fixed cost per launch that a bigger tensor amortizes. The 129280-row case is within
3 % of its in-situ duration in the pass (2639 us measured in the trace), so for the big shapes this harness
and the pass agree. For the medium ones they do not: in situ the 16384-row launch is 109 us against 148 us
here, and a 4096-row launch is 63 us against 152 us, which is faster than the DRAM ceiling and therefore
L2 rather than a measurement of the same thing. The isolation is a fair reading of a single launch and a
poor model of a graph that runs 500 of them back to back, so tuning the medium shapes against it would be
tuning the wrong number.

MMQ forced (`GGML_FORCE_MMQ`, which skips the matrix-vector dispatch) changes none of these by more than
2 %, so the crossover is not at this batch size: the quantized matmul path is not the fix for the dense
term, and the case for it is closed.

Also settled here, from the reference's own model directory: the weights the comparison is against are
**fp8 (e4m3, 128x128 blocks) for everything except the experts, which are fp4** (`config.json`,
`quantization_config` + `expert_dtype`). Our GGUF puts the experts in MXFP4 and the dense tensors in
Q8_0, which is the same split at the same precision (34 bytes per 32 against 8.004 bits per parameter,
6 % more bytes), so the two read the same bytes and the gap is implementation, not quantization.

--- 2026-09-15, third attempt: the peer's CUDA graph replays the pointers it captured ---

The build with the length check loaded correctly, the update path ran, the gates passed on the update arm,
and the client then aborted with `Remote RPC server crashed or returned malformed response`. The peer's
backtrace ends at `ggml_backend_cuda_synchronize` under `rpc_server::set_tensor`, which is the same place
the first attempt died: a synchronize that fails because the CUDA context was already poisoned by an
earlier launch reading or writing the wrong address.

What the peer's side actually does with the new pointers is in `ggml-cuda.cu:2923`, and it is the bug:

- `ggml_cuda_graph_update_required` holds one captured graph per graph object, keyed by `nodes[0]`, and
  returns early, with **no comparison at all**, when `cgraph->uid != 0 && cgraph->uid == graph->uid`;
- an update changes every tensor's `data` and leaves `uid` alone, so the early return fires and the
  captured launches replay with the addresses they were captured with. The comparison that would have
  caught it (`node_src_data_ptrs`, copied per node) never runs;
- the client believes the graph ran with the new pointers, the peer ran the old ones, and the allocator
  has since handed that memory to a tensor of another size, so the fault is only a matter of time.

The fix is for the uid to move with the pointers, which is exactly what the CUDA backend uses to decide it
has to look: `sg.graph->uid = request.new_uid` before the compute. Nothing else changes, and the cost of
the path stays well under the full rebuild, because the backend's response is a per-node property compare
and a `cudaGraphExecUpdate`, not a context and a graph construction.

A second bug in the same path, not reached yet in this run because the first update is what died: after
sending an update the client kept the **old** uid in the map it keys updates on, while the peer had moved
the entry to the new one. The second graph of the same structure would then have asked the peer for a uid
it no longer had, which is a `return false`, which closes the connection, which is the same abort. The
client now re-points that map at the new uid in the same place it re-points `graph_uids`.

Baseline, worth recording on its own: one resend arm with `--reps 3` gives **41.5 tok/s, min 41.0, max
41.5, spread 1.4 %**, against the 28 % spread the same arm showed at `--reps 2`. Every arm from here on
runs three reps; a 1.4 % spread is what makes a 10 % result readable at all.

--- 2026-09-16, the host side, and a correction: 8.8 s of memcpy time is waiting, not waste ---

The client's host-side CUDA API time over the whole capture, which no earlier entry had looked at:

| call | n | total ms | avg us | max us |
|---|---|---|---|---|
| cudaMemcpyAsync | 9,805 | 8,795.5 | 897 | 93,589 |
| cudaGraphLaunch | 9,768 | 1,209.2 | 124 | 1,141 |
| cudaLaunchKernelExC | 89,146 | 316.2 | 3.5 | 9,737 |
| cudaStreamSynchronize | 22,694 | 138.8 | 6.1 | 69 |
| cudaGraphInstantiate | 196 | 71.3 | 364 | 2,324 |

8.8 s of host time in memcpy looked like a finding, and the largest calls turned out to be one shape:
**112 calls of 3,102,720 bytes, device to host**, one per pass. 3,102,720 is 129280 x 6 x 4, the logits for
the six verified positions, and the call is `llama-context.cpp:1506`,
`ggml_backend_tensor_get_async(backend_res, t_logits, logits.data, ...)`.

**The correction**: each of those calls is 78 ms on the host and **60 us on the device**. Nothing copies at
40 MB/s. What the host is doing is blocking, because the destination is pageable and the driver makes such
a copy synchronous, and the copy is queued behind the pass's graph, so it completes when the graph does. The
8.8 s is the host waiting for the GPU, which is the design, not a defect. This entry therefore withdraws its
own first reading, made earlier in this same session, that the host was spending a pass's worth of time in a
copy.

Allocating the output buffer from a device host buffer (pinned) instead of the pageable CPU one, which is
what `output_reserve` falls back to when the output device, here the RPC or meta device, exposes no host
buffer of its own, was implemented and then **deliberately not built or measured**: with the copy being a
wait rather than waste, the best case is moving the wait from one call to another, plus about a millisecond
of bounce-buffer traffic a pass. It is recorded here as an idea that the profile does not support.

What the table does establish is the shape of a pass: **106 ms of kernel time plus about 8 ms of host tail**
(the logits arriving, the CPU sampler over 129280 logits a position, and the next dispatch), which is the
1-10 ms gap bucket the earlier entry measured. And what it says about the floor is what matters for the goal:
the weight traffic a rank must read for six verified tokens is 15.7 GB, 69 ms at the rates these kernels
actually reach, so a llama.cpp pass with *no* allreduce, *no* small kernels, *no* draft and *no* host tail
would be about 69 ms, 65 tok/s at the 4.52 accepted tokens a pass this draft gives. The reference's 63.1 is
65 tok/s of equivalent. There is no single change left that reaches it; what is left is the 13.4 ms of
collective, the 12.3 ms of small kernels and the 7.1 ms of draft, and each of those is engineering rather
than a switch.

--- 2026-09-16, confidence-truncated drafting: the head works, the engine pays more than it saves ---

The dspark draft carries a confidence head (the converter exports `DSPARK_CONF_PROJ`), and
`common/speculative.cpp:1268` reads it: with `--spec-draft-p-min P` the draft stops at the first position
whose confidence is below P. That is the one mechanism that could cut a pass's MoE work without losing
accepted tokens, so it was run at P = 0.5:

| | p_min 0 | p_min 0.5 |
|---|---|---|
| draft tokens a pass | 4.98 | 4.58 |
| acceptance per draft token | 0.707 | **0.756** |
| accepted tokens a pass | 4.52 | 4.31 |
| eval ms a token (512-token reps) | 27.08 | 30.44 to 36.86 |
| c1 median | 38 to 41 | **29.8** |

Two things in that table are real and one is fatal. The head is *calibrated*: truncating raises the
acceptance per draft token from 0.707 to 0.756, so the positions it drops are the ones that were being
rejected. And the truncation *fires*: 4.58 draft tokens a pass against 4.98, and the accepted count only
falls by 0.21. But the pass gets **15 % more expensive per token**, so the net is -25 %.

The mechanism is the batch shape, and this record already has the evidence for it: the verify batch varies
between 4 and 6 from pass to pass, so the target's graph and its captured CUDA graph are a different one
every time, against 8875 warmup resets to 9240 completions measured earlier. The two tokens saved on the
MoE cost about 16 ms; the graph churn costs more. **Closed**, and it closes the whole family: in this engine
a fixed verify batch is worth more than any saving that comes from varying it, so schemes that shorten the
verify per pass are losses before their arithmetic even matters.

What that leaves as the honest arithmetic for the goal, with the reference's own config now in hand (same
43 layers, same 256 experts top-6, same fp8/fp4 split, same `dspark_block_size = 5`, and its draft is the
same three MTP layers we already run): a rank reads 15.7 GB for the target plus 5.2 GB for the draft,
20.9 GB a pass, which is 90 ms at the 232 GB/s this pair reaches and 77 ms at the DRAM peak, for 4.52
accepted tokens. That is 50 tok/s of *nothing but weight traffic*, and the reference reports 63 to 65. The
difference is not a knob, a config, a protocol or a batch shape; it is that its kernels and its fused graph
move the same bytes in about two thirds of the time.

--- 2026-09-16, the host tail is the CPU sampler chain, and min_p was four fifths of it ---

The host tail a pass leaves after the graph was the last unattributed part of the budget, ~5 ms of GPU idle
twice a step in the trace. It is the sampler: this engine samples on the CPU, and two logits arrays come back
over the wire every step (2,585,600 bytes for the draft's five positions and 3,102,720 for the target's six,
both in the memory-copy table of the capture), so a step runs **eleven full-vocabulary passes** through the
sampler chain.

`.scratch/sampler-cost.cpp` measures that chain directly, with no model and no GPU: it builds the server's
default sampler list over a 129280-candidate array and times each stage's `llama_sampler_apply`. The list is
nine stages (penalties, dry, top_n_sigma, top_k, typ_p, top_p, min_p, xtc, temperature) and with the server's
default parameters only three of them do work:

| stage | ms a position |
|---|---|
| top_p (0.95) | 0.182 |
| **min_p (0.05)** | **0.947** |
| temperature (0.8) | 0.033 |
| the other six | 0.000 |
| **whole chain** | **1.163** |

Eleven positions at 1.163 ms is **12.8 ms of CPU a step**, which is the gaps the trace shows.

`min_p`'s unsorted path builds a `std::vector` of survivors with a `push_back` per survivor and then copies
them back, three passes over the vocabulary and an allocation per call, for what is a threshold test. Compacting
in place keeps the same tokens in the same order:

| | ms a position | whole chain, 11 positions |
|---|---|---|
| upstream | 0.947 | 12.79 ms |
| in-place | **0.121** | **3.71 ms** |

**7.8x on the stage and 9 ms of CPU a step off the chain.** Because the token set is identical the acceptance
line is an exact check, and the change is behind a file switch so the paired protocol can time it; that run is
what decides whether the CPU saving reaches the pass. This is the first thing found this session that is a
plain speedup rather than a configuration or a geometry, and it is upstream code rather than this fork's own.

--- 2026-09-16, the min_p change was dead code, and the sampler measurement was synthetic ---

The entry above ends on the paired run being what decides whether the CPU saving reaches the pass. That run
came back a null: 26.66 against 28.83 ms a token, 37.6 against 34.4 tok/s, nine rotated rounds each. The
entry above is wrong about why, and this corrects it.

**The in-place path never executed.** `min_p`'s fast path was written behind `if (!cur_p->sorted)`, on the
reading that the candidate array reaches `min_p` unsorted. It does not. `llama_sampler_top_p_apply` ends with
`cur_p->sorted = true` (src/llama-sampler.cpp), and in the default chain `top_p` runs before `min_p`. So by
the time `min_p` is applied the array is sorted, the whole `!cur_p->sorted` block is skipped, and both arms
ran identical upstream code. The 7.8x on the stage in the table above is real for that stage, but it was
measured on a code path this server never takes.

**The synthetic logits in `.scratch/sampler-cost.cpp` are flat, and flat logits are the worst case for
`top_p` and the best for nothing else.** A flat distribution over 129280 candidates makes `top_p` keep
thousands of tokens and makes `min_p` reject almost none, so the per-stage costs in that table are an upper
bound at best. On real logits `top_p` cuts the array to a handful before `min_p` sees it, so `min_p` over
whatever is left is not four fifths of the chain however it is implemented.

Both facts point the same way: the sampler chain is not established as the host tail, and the 12.8 ms a step
figure quoted above is withdrawn. The gaps in the trace are unattributed again, and the next question is
where in the step they sit, which the server's own `DEBUG_TIMINGS` block answers: it times pre_decode, the
draft inside it, decode, post_decode, the two sampler calls and the verify.

--- 2026-09-16, the phase split: the host tail is the draft, not the sampler ---

The server's own `DEBUG_TIMINGS` block, upstream code that had never been enabled here, turns on four
accumulators over pre_decode, decode, post_decode and the non-speculative sampler call. Two more were added
for this run, one around `common_speculative_draft` inside pre_decode and one around the verify inside
post_decode. The block also forces `llama_synchronize(ctx_tgt)` after each decode, so the phases are
serialized in a way the release build is not: read the split, not the absolute rates.

Cumulative averages from the first 460 passes (gates passed, acceptance 0.70693, mean len 4.52):

| phase | ms |
|---|---|
| t_pre_decode | 24.1 |
| t_decode | 103.9 |
| t_post_decode | 7.9 |
| t_draft (inside pre_decode) | 24.0 |
| t_verify (inside post_decode) | 7.9 |
| t_sampl (non-speculative path, unused here) | 0.66 |

Those sums to 136 ms a pass against a wall of 117, which is the tell: the averages are cumulative from
startup and the early passes are much slower, so they are not the per-pass cost. The marginal cost over the
last two print windows, 46 passes each, is what to use:

| phase | marginal ms a pass |
|---|---|
| pre_decode | 17.3 |
| decode | 88.4 |
| post_decode | 3.8 |
| **sum** | **109.5** |
| wall, same window (5.040 s / 46) | 109.6 |

Three things follow, and the first one corrects the entry above.

**The verify is 3.8 ms a pass, 3.5 %, and the sampler chain is not in it.** The chain measures 0.091 ms a
position on realistic logits, 0.55 ms for the six the target samples, so what the 3.8 ms holds is the logits
fetch and the accept bookkeeping, not sampling. The 12.8 ms that the min_p entry attributed to the sampler,
and the ~8 ms host tail attributed to it again afterwards, are both withdrawn.

**The draft is 16.4 ms a pass of the 17.3 ms pre_decode, so 15 % of the pass is the draft call**, and about
7 ms of that is the draft's own kernel time (5.6 ms of bf16 matmuls plus its MoE). The other ~9 ms is inside

`load_dft`), and five sampled positions whose logits come back from the device. This is the largest
unattributed item left that is ours, and no earlier entry had separated it from the target's pass.

**The target's decode is 88.4 ms a pass**, which is the kernel budget the nsys capture lists as 106 ms for
the whole pass minus the draft's share, and the collective's waiting is inside it.


--- 2026-09-16, a longer dspark block is closed: the head is trained for five positions ---

The reference's own engine log says `num_speculative_tokens=7`, eight verified positions against our six,
and the record above read that as the reason its per-step overhead is amortized over more tokens. The block
size is what stops us from doing the same: `dflash.block_size` in the draft's metadata is 5, the impl clamps
`n_max` to it, and the entry that closed `n_max 7` concluded the draft emits five tokens whatever the flag
says. That entry could not test what a longer block would do, because the flag was clamped before it reached
the block.

It can be tested now. `common_speculative.cpp` gained a file switch: `GGML_DSPARK_BLOCK` names a file holding
a draft length, read per draft call, and while it exists the trained block is widened to it. Arm `off` is the
trained five; the file's contents are the block for the other arms. One server, four lengths, the paired
protocol with rotation, five rounds:

| arm (block) | ms a token, five reps | median | c1 tok/s, median |
|---|---|---|---|
| off (5) | 26.51 25.45 33.18 25.52 27.92 | **26.51** | **36.8** |
| 7 | 49.68 47.06 43.87 47.67 44.28 | 47.06 | 21.0 |
| 9 | 51.24 56.91 51.07 49.80 52.59 | 51.24 | 19.3 |
| 11 | 54.62 65.82 55.15 50.09 52.66 | 54.62 | 18.1 |

The acceptance line says why, and it is not a cost problem: **at block 5 the draft accepts 0.70693
(398/563) with mean len 4.52; in the longer arms the same counter reads 0.13747 (306/2226) with mean len
2.50.** The head denoises the whole block jointly against the mask tokens it is given, so widening the block
degrades every position, not just the new ones: the accepted run per pass falls from 3.52 to under 1.5 while
the pass cost rises, which is the doubling in the table.

So the five-position block is a property of the trained head and not a knob, and **the "amortize the
per-pass overhead over a longer verify" route is closed for this model.** Whatever vLLM does with
`num_speculative_tokens=7`, it cannot be reading seven positions out of this head's single denoising pass,
and the reference's 4.73 accepted against our 4.52 is not a step-size advantage it is getting for free.

The switch is removed again after this run: it is a lever for the dflash family in general, not for this
goal, and the numbers above are what it was for.

The harness lesson from the same run: the `mean len` field this record treats as the correctness check is
printed only when a request completes, and the pattern in `.scratch/paired-run.sh` expects one space where
the server writes two ("mean len =  2.50"), so the three new columns read `len0` in every arm. The acceptance
figures above came from the log afterwards and are what the arm actually produced.

--- 2026-09-16, where the peer's host goes, and how much of the pass is spent dispatching ---

Two more instruments on top of the phase split. Client side, `GGML_META_PROF=1` times the whole of
`ggml_backend_meta_graph_compute` (the host time to plan and dispatch a decode's graph) and buckets it by
graph size so the draft's decode and the target's separate. Peer side, the existing `GGML_AR_SRV_PROF=1`
times every command in its request loop. One c1 run, three reps, gates passed, acceptance 0.70693 as always.

The peer, from the marginal window of the last 2,000 graph dispatches (44,000 total over four reps, 452
passes, so **97 dispatches a pass**, 82 % of them recomputes):

| peer path | per pass | us each |
|---|---|---|
| `GRAPH_RECOMPUTE` (uid hit, replayed) | 79.7 | 26.9 |
| `GRAPH_COMPUTE` (whole graph re-sent) | **17.3** | **527** |

**17.3 of 97 dispatches a pass are full resends at 527 us of peer host each, 9.1 ms a pass**, and the rest
cost 2.1 ms, so the peer's host is busy about 11 ms of a 109 ms pass. The 527 us corrects the 2,553 us this
record has been quoting for the same path since 2026-09-15: that measurement was taken over a window that
included the load, which sends tens of millions of `set_tensor` commands.

The client, from the same run, host time inside the meta backend's dispatch loop, marginal per five-second
window (46 passes): the **target 4.2 to 9.6 ms a pass** with the swings landing on the intervals that carry
the resends, the **draft 2.1 ms a pass**. So of the draft's 16.4 ms call, 2.1 ms is the graph dispatch and
about 7 ms is its own kernels; the rest is inside `llama_decode` and the five sampled positions, which is now
the only part of the draft left unattributed.

What that says about the collective: the client's host is not blocked in the dispatch loop (4 to 10 ms of a
109 ms pass), so the 13.4 ms of allreduce kernel time it sees is mostly its GPU waiting for the other rank,
and the other rank's host is busy 11 ms a pass with 9.1 ms of that on the resends. The resends are the one
term in this record that is measured on both ends of the link and has a mechanism: the client re-serializes
about a hundred tensors per resend, the peer rebuilds the graph, and both ends are inside the client's
collective wait.

Two caveats on this run's instruments. `sub/call` and the two dispatch columns in the meta profile print
zero: the guard was written to copy its counters by value at construction, so it reports the values they had
before the call. That is fixed and the columns will be real on the next run. And the client's cache
diagnostic from the earlier entry reports 255,811 RPC dispatches over "a full run", 566 a pass if that run
was four reps, which does not agree with the peer's 97 a pass in this one; one of the two is counting
something else and this entry does not know which.

--- 2026-09-16, the graph update rebuilt on identities: correct, converts, and still not a win ---

The update path was rebuilt around the one thing that makes it safe. `rpc_tensor.id` is
`reinterpret_cast<uint64_t>(tensor)`, the client's own tensor pointer, so it is a stable identity for a
tensor across passes even when its data pointer moves, and the client can collect the identities and the
pointers in `add_tensor`'s order without building the rpc_tensor structs. The client now keys a small list
of graphs per structural key, each carrying the identities that full message was sent with; a uid miss
collects the current identities once and sends an update only when they match a graph the peer still holds.
The peer stores the identity list against the graph and applies an update only when the identities it
receives are that list, tensor for tensor. Two changes follow from the failure modes this record already
paid for: the client never sends an update the peer can refuse (a refusal is fatal to the connection by
design, so it is checked on the client), and the peer dispatches an updated graph with uid 0 so the CUDA
backend's reuse path, which trusts a matching uid without comparing nodes, cannot replay the pointers it
captured. The new uid goes back on afterwards for the recomputes that follow.

It runs. Nine rotated paired rounds, `off` against `on`, one 512-token rep each, gates passing on the first
arm, **and `mean len = 4.52` in all eighteen reps**, so no pointer was written into the wrong tensor:

| arm | ms a token, nine reps | median | c1 tok/s |
|---|---|---|---|
| off | 29.00 27.43 25.36 24.72 27.58 29.12 24.34 24.34 25.33 | **25.36** | 38.3 |
| on | 24.22 24.50 24.16 28.30 25.54 32.70 28.20 33.42 28.25 | 28.20 | 34.5 |

**That is not a win and it is not cleanly a loss either.** The paired differences per round (off minus on)
are +4.78 +2.93 +1.20 -3.58 +2.04 -3.58 -3.86 -9.08 -2.92: four rounds favour the update, five favour the
resend, and the median says the update is 2.9 ms a token slower. What breaks the tie against it is the

--- 2026-09-16, the phases are GPU waits, and the sampling loops pay a synchronize per accessor ---

Two more instruments, both client side. `SRV_LLAMA_PROF=1` splits the target's decode into `llama_decode`
and the `llama_synchronize` the server already calls after it; `GGML_DRAFT_PROF=1` splits the draft call into
its own `llama_decode` and its block sampling. One c1 run, three reps, gates passing, acceptance 0.70693.

| what | marginal ms |
|---|---|
| target `llama_decode` | ~89 a pass |
| target `synchronize` right after | **0.15 to 0.4** |
| draft `llama_decode` | **13 to 16** |
| draft block sampling (5 positions) | **3.0 to 9.3** |

The first row corrects the reading of the phase split: `llama_decode` costs 89 ms a pass and the
synchronize after it returns in a fraction of a millisecond, which cannot be true of host work. It is not:
**`llama_decode` ends by copying the logits of every output position to the host, and the destination is
pageable, so the host blocks in that copy until the graph completes.** The 89 ms is the target's GPU pass,
not its host cost, and the same is true of the draft's 13 to 16 ms, where that copy waits on the draft's own
graph. The earlier entry's "13 ms of wait inside the target" is withdrawn with it: the target's phase is
essentially all GPU.

What the run does establish is the two sampling rows, which are host work. Five draft positions cost 3.0 to
9.3 ms and the verify's four to five positions cost 3.8 ms, against 0.09 ms of chain work a position. The
reason is in `common_sampler_sample` and `set_logits`: the first calls `llama_synchronize(ctx)` and the
second calls five more accessors (`llama_get_logits_ith`, `llama_get_sampled_probs_ith`,
`llama_get_sampled_logits_ith`, `llama_get_sampled_candidates_ith`, and two count getters), **and every one
of them synchronizes the context.** A sampled position therefore waits for the device six times over, and on
a context whose schedule includes an RPC backend that wait is a round trip through the peer's inbox rather
than a stream check. Eleven positions a pass is roughly sixty waits.

The logits for every output position are copied to the host once, at the end of the decode, so the later
waits cannot find new data. `llama_sync_defer(ctx, true)` makes `synchronize()` return while set, the common
layer holds it around a run of positions after one real synchronize, and the whole thing is behind
`GGML_SAMPLE_SYNC_PATH`. The paired run against it is in flight; the numbers above are why it is worth one.

--- 2026-09-16, the sampling synchronizes are real host work and are not on the pass's critical path ---

The change: one real wait per sampling run instead of six per position, `llama_sync_defer(ctx, true)` making
`synchronize()` return while the common layer samples a block, behind `GGML_SAMPLE_SYNC_PATH`. The
instrumentation above says the draft's block sampling is 4 to 12 ms; with the deferral the same window reads
**0.8 to 2.3 ms**, so the mechanism is confirmed at the level it was aimed at and about 29 waits a pass are
wasted work.

Nine rotated paired rounds say that does not reach the pass:

| arm | ms a token, nine reps | median | c1 tok/s, median |
|---|---|---|---|
| off | 27.14 28.81 26.59 23.91 31.50 31.26 28.66 24.58 29.59 | 28.66 | 34.0 |
| on | 28.25 23.63 23.52 28.57 29.82 29.04 23.76 25.26 30.45 | 28.25 | 34.2 |

Paired differences (off minus on): -1.11 +5.18 +3.07 -4.66 +1.68 +2.22 +4.90 -0.68 -0.86, median **+1.68 ms**
and mean +1.08, against a spread of 5 ms between rounds on identical arms. Acceptance 4.52 in all eighteen

The interesting part is why the two readings disagree, because it says where the pass is actually bound. The
draft's sampling waits are waits on the *peer*: `llama_synchronize` on a context whose schedule holds an RPC
backend queues a dummy message and waits for the other rank to process everything already in flight, and the
other rank is busy with its own half of the draft's graph. So the client's sampling time is the peer's work
seen from the client, and removing the wait moves it into whatever the client waits on next rather than out
of the pass. The same reading explains the earlier entry's stall experiment and the update path's
contradictory rounds: **the client's host is not the limiter, the pair's GPU pipeline is**, and the numbers
on the client's side that look like host work are partly the other rank's queue.

That is the third lever this session that measured as real work on the client and did not move the pass
(rows per block, the graph update, this one), and the pattern is now explicit enough to record as a rule: on
this rig, a change to the client's host path is only worth a rig cycle if it removes a *dispatch* or a
*kernel*, not a wait.

--- 2026-09-16, a decode decomposed, and the draft runs twice a pass ---

`LLAMA_CTX_PROF=1` cuts a decode into the graph build plus scheduler allocate, the dispatch, and the logits
copy at the end. One c1 run, three reps, gates passing, acceptance 0.70693. Marginal per five-second window,
per call:

| bucket | calls a window | build | dispatch |
|---|---|---|---|
| draft (graph < 1,000 nodes) | ~95 | 0.74 ms | 2.3 to 4.0 ms |
| target (graph >= 1,000 nodes) | ~47 | 0.4 to 1.6 ms | 5.4 to 22 ms (mean 12.2) |

**The graph build and the scheduler allocate are cheap**, which closes the hypothesis that the pass pays for
rebuilding and re-splitting the graph every step. The copy column is zero: the logits copy returns before the
data arrives and the wait lands in the next synchronize, which is why the deferral experiment above could
remove so much measured sampling time without moving the pass.

**The draft bucket runs twice per target decode, about 95 calls against 47.** That is not a measurement
artefact and it has a name in the code: `tools/server/server-context.cpp:3805` calls
`common_speculative_process(spec, batch_view)` after every target decode, and for a dflash draft that is the
KV injection, `llama_decode(ctx_dft, batch_inject)` at `common/speculative.cpp:1213`, which feeds the
target's extracted layer features into the draft's cache for the batch just verified. So a pass is **two
draft forwards and one target forward**, the injection inside the target's phase and the noise block in
pre_decode, and the server's own comment above that call says the re-evaluation is done for simplicity
(`[TAG_SPEC_AVOID_DRAFT_REEVAL]`).

Two consequences. The 13 to 18 ms the phase split called "the draft" is the noise block alone, and the
injection's cost is hidden inside the 88 ms "decode" phase, which the record has been reading as the target;
the true split of a pass is three forwards, not two. And the dispatch column is now the largest host item
measured on the client: 12.2 ms a pass for the target against the 5.5 ms the meta backend reports for its own
part of the same call, so about 6.7 ms is the scheduler between the splits, which is copies and event waits
across an RPC boundary and is a dispatch rather than a wait.

What this does not yet say is how much of the injection's own time is the draft's kernels and how much is
launch, which is the next thing to instrument if the draft's two forwards are to be attacked.

--- 2026-09-16, the cuda launch bill, and what the client's dispatch really is ---

`GGML_LAUNCH_PROF=1` counts every `ggml_backend_cuda_graph_compute` call: whether it replayed a captured
graph or evaluated the nodes directly, the host time of each, and the instantiate and re-point counts. Run
together with `GGML_META_PROF` and `LLAMA_CTX_PROF`, so all three levels come from the same passes. At 41
tok/s and 4.52 tokens a pass there are 45 passes in a five-second window, and the client makes 3,135 calls
in it: **70 CUDA dispatches a pass.**

| per call | cost |
|---|---|
| captured-graph replay | **17.6 us** (2,861 calls a window, 63.6 a pass) |
| direct evaluation | **184 us** (274 calls a window, 6.1 a pass) |
| instantiate | 215 us, 175 in the whole run (under 2 a pass) |
| re-point (update executable) | 35 to 47 us, 962 in the run |

So the whole launch bill is **2.2 ms a pass**, 2 % of it, and the arithmetic that the record has been
carrying (88 launches at the 124 us an nsys host table reported = 10.9 ms) is withdrawn: **that 124 us figure
does not reproduce.** What the same run shows for the dispatch levels above the launches is that they are
much bigger and much noisier:

| level | marginal ms a pass |
|---|---|
| CUDA launches (all calls) | 2.2 |
| meta backend's dispatch, target decode | 2.5 to 10.7 |
| scheduler's dispatch, target decode | 2.5 to 19.6 |

with the swings landing on the windows that carry RPC resends. So the client's dispatch is real host work of
about 8 ms a pass, of which the kernel launches are only a quarter: the rest is the meta backend's subgraph
loop and its serialization, and the outer scheduler's split bookkeeping and copies. That is the same shape as
the peer's own 9 to 11 ms a pass, and the two together against a reference that launches **one** captured
graph per step is the structural difference this record has been circling: 70 dispatches, 70 RPC messages and
about 17 peer graph rebuilds a pass, against one.

It also says what not to do: making the client's host path cheaper by removing waits (the deferral) or by
converting resends (the update path) cannot pay more than the dispatch they sit in, and both measured at or
below the noise.

The two-rank microbenchmark, swept over NCCL_ALGO and NCCL_PROTO at the sizes the pass uses. NCCL parses its

largest device-side term: a few environment variables would have cost nothing to set. Since the fix for
jitter is fewer sync points, and the sync points are two per layer by the tensor-parallel scheme, the
collective's 10 ms a pass of waiting stands unless the parallelisation changes.

Recorded too: NCCL_ALGO=Ring NCCL_PROTO=Simple is worth about 18 us a collective over the defaults on this
fabric, 1.5 ms a pass if every collective behaved like the microbenchmark. It is free to set, needs an A/B/A
across loads to confirm on the pass, and is the smallest of the items left; it is not adopted here.

Why this is worth a cycle: the host work at those boundaries is not inherently serial with the device. The
injection depends on the target's layer features, not on the sampling or the accept, so the injection can be
issued immediately after the target decode and the sampling done while it runs. That is a reordering of the
server's per-step flow, it is switchable at runtime, and it is the first candidate this session with an
expected effect above the rig's resolution.

Two things follow from the stall's location, and both are worth writing down before the next attempt.

**The obvious reorder is not available.** The first thing the location suggests is to issue the injection right
after the target decode and sample while it runs, since the injection reads the target's layer features and
not the sampling's result. That is wrong: `post_decode`'s speculative branch *rolls the draft's context back
to a checkpoint* whenever fewer than all drafted tokens are accepted (`ckpt.load_dft`, `tools/server/server-context.cpp:4010`),
which with an acceptance of 4.52 of 5 is nearly every pass, and a rollback after the injection would discard
it. The injection has to stay behind the accept and its rollback.

**The candidate for the 13 ms is the draft's own checkpoint traffic.** `common_prompt_checkpoint` keeps
`data_dft` and `update_dft` / `load_dft` save and restore the draft's partial state (`common/common.h:1165`),
and with the draft tensor-split across both nodes a save or a load is a transfer that crosses the RPC. They
run at `server-context.cpp:3073` and `3144` in pre_decode and at `4010` on the rollback, so two or three a
pass, and the record's own note on the same code path (`[TAG_SPEC_AVOID_DRAFT_REEVAL]`, "for now, always
re-evaluate for simplicity") says upstream knows this work is done more often than it needs to be. The state
is small (a 3-layer draft over a few hundred positions, megabytes at most), which is why this entry does not
claim it is the 13 ms; it claims that it is where to look, and that the instrument for it is a timer around
the save, the load, the logits copies and the sampling in the server's step, which is the next measurement.

| of which under 5 us | 4,770 |

| so nodes a subgraph | ~72 |
| host dispatch per kernel (65 ms / 6,295) | **~10 us** |

So **the host launches a kernel in about 10 us and the device runs the small ones in about 2**, and the 4,770
small kernels are ~48 ms of the host's 65 ms against ~9 ms of device time. The pass is not short of device

compiled into this build. `GGML_CUDA_PDL=0` takes the plain launch and skips the lookup, so an A/B/A of three
loads against it measures the whole heavier path at once; that run is in flight.

--- 2026-09-16, correction: the host's launch rate is not the limiter, the dependency chain is ---

The last two entries built an argument on the host's launch rate: ~10 us a launch against a device that
consumes a node in ~29 us, so the host is only 17 % ahead and the ~19 ms of idle is starvation. The
CUDA-graphs-off result contradicts that, and the contradiction is in this record: **with graphs off the host
launches every node itself, 65 ms of a 109 ms pass, and the pass is faster, not slower.** The host is not
starved and has 44 ms of slack. A pass that pays 65 ms of host time against 109 ms of device time has room to
launch more, not less, and removing launches to "let the host keep up" is chasing a term that is not binding.

What the same evidence does support, and it is a different mechanism, is the **dependency chain**. PDL is worth
24 % on this workload (41.1 against 33.1 in the arm above, with a 3.5 % spread on the slow arm), and PDL is
exactly a mechanism for overlapping the *launch* of a kernel with the execution of the one it depends on. A
24 % swing from that says the pass is bounded by kernel-to-kernel dependencies, not by bandwidth or by the
host: every kernel is a serial step, and the steps that cross ranks are the expensive ones. At ~220 us of
arrival latency per collective over ~86 collectives a pass, the ~19 ms of idle is that term, and it is the part
PDL cannot hide.

Fusion still pays, but for the dependency reason rather than the host-rate one: fusing N kernels into one
removes N-1 serial steps from the chain. The gate chain is the largest group left (~690 launches a pass: about
173 each of sigmoid, add, mul and scale, four a layer across the two hyper-connection chains, two for
attention and two for FFN). It is computed *outside* the three fused kernels that already exist and run
(`dsv4_hc_pre_f32` 23,011 launches a run, `dsv4_hc_post_f32` 23,011, `dsv4_hc_comb_f32` 23,012), and those
kernels already take the gate as an input, so folding means passing the raw mixing output plus the scale and
base views and evaluating `sigmoid(mixes*scale + base) + eps` (or `*2` for post) inside them. The plan is
recorded here for the next cycle; it is a change across the op's signature, its CUDA implementation and the
model's graph builder, with the gates and the acceptance line as the correctness check.

--- 2026-09-16, the gate fold's real price, and going back to the collectives ---

The fold planned in the entry above was priced at ~10 us a launch, which is the *host's* cost per launch, and
the host has 44 ms of slack in a 109 ms pass, so that price does not convert to pass time. In the
dependency-chain model the fold is worth the *serial step* it removes, which is the kernel's own execution
(~2 us) plus whatever launch or dependency latency PDL does not hide (a few us). At ~690 kernels that is 1.4 to
3.5 ms, 1 to 3 %, and **below this rig's resolution**. It is still worth doing eventually, because it is
strictly fewer steps and the correctness check is the acceptance line, but it is not the next cycle.

What is worth the next cycle is the term the same model puts first: the **86 collectives at ~220 us of arrival
latency each, ~19 ms a pass**, which is the 19 ms of idle. Three explanations have been excluded by
measurement (the peer's host, the client's host, the NCCL configuration), and the fourth is the peer's *start*
lateness: the client hands the RPC rank split i only when it reaches it, so the peer's receive, deserialize and
launch land inside that split's collective. That is what `GGML_TP_PREFETCH` exists to remove, by handing the
peer split i+1 before dispatching split i.

This record already called the prefetch a null, on an A/B/A of **three reps an arm** whose arms read 40.5,
40.4 and 38.9, and it flagged the same arm's 11 % drift in that entry. Three reps cannot resolve a term this
size, and the protocol this session adopted after that entry, rotated single reps with both metrics, can. The
re-run is in flight, under the graphs-off default and with fifteen rounds.

--- 2026-09-16, the ring fixed, the accounting closes, and the tax is per kernel ---

The allreduce instrument's ring was 256 entries against ~3,900 allreduces in a five-second window, so it filled
fifteen times over and dropped most of its windows; the 7.7 ms a pass it reported was a lower bound and the
entry above flagged it as the soft number in the accounting. At 4,096 entries the drops fall from 6,323 to a
few hundred and the figure is 6.7 ms a pass over ~74 to 100 us a collective, which is where the nsys capture's
7.4 ms already was. **The collectives are ~7 ms and always were.**

So the accounting over a 109 ms pass is now closed from three independent instruments:

| term | a pass | how measured |
|---|---|---|
| subgraph windows | **86 ms** | CUDA events around every `ggml_backend_cuda_graph_compute` |
| collectives | **6.7 ms** | CUDA events around every `nl` world allreduce |
| gaps between windows | **24 ms** | the same events, differenced |
| idle, gaps less the collectives | **~17 ms** | derived |

86 + 6.7 + 17 = 109.7, and the pass is 109. The 17 ms is the item five explanations have now been excluded
from (the peer's host, the client's host, the NCCL configuration, the peer's message delivery, the peer's own
subgraph time), and the arithmetic says what it is without another probe: **6,295 kernels a pass and ~2.7 us of
latency each**, which is the time the device takes to retire one kernel and start the next when PDL cannot
cover the dependency. It is a tax on the *number of kernels*, not on bytes, not on launches by the host, and
not on any single kernel's speed.

That is what the last several cycles have been converging on from four directions, and it is now the statement
to act on:

- CUDA graphs off won 7.7 % by removing the *device's* replay cost per node, and the host absorbed every launch.
- PDL is worth 24 %, and PDL is a mechanism for covering exactly this per-kernel dependency latency.
- The graphs-off host cost, 65 ms a pass, has 44 ms of slack, so the host is not the term.
- And the idle is 6,295 kernels times ~2.7 us, which no configuration change can remove.

**The only lever left that acts on it is fewer kernels.** At ~2.7 us each, a pass that fused away a quarter of
its 6,295 kernels would gain ~4 ms, 4 %; the whole small-kernel pile of 4,770 sub-5 us kernels is worth ~13 ms
if it could all go, which it cannot, but it sets the scale: this is now a kernel-count programme, and each
fusion should be priced at 2.7 us a kernel removed rather than at the kernel's own duration.

--- 2026-09-16, the kernel count stands: the earlier withdrawal divided by the wrong pass count ---

An earlier entry withdrew the claim that a pass runs about 5,200 kernels, on the kernel census in

The correction matters beyond its arithmetic: the entry it corrects is the one that sent this line of work away

--- 2026-09-16, the hyper-connection gate chains fold into one kernel, and a launch is worth ~2 us ---

The hyper-connection gate is the largest count of fusable nodes in the model, and it is now folded. From
`src/models/deepseek4.cpp`, each of the two sites a layer builds the gate as

    pre  = view_2d(mixes, hc, nt, 0)                 // 24 element mixing output
    pre  = mul(pre, scale_pre); pre = add(pre, base_pre); pre = sigmoid(pre); pre = scale_bias(pre, 1, eps)
    post = view_2d(mixes, hc, nt, hc); ... sigmoid, scale 2

and hands it to `DSV4_HC_PRE` (src[1]) or `DSV4_HC_POST` (src[2]). Four nodes a site, 172 sites a pass
(86 pre + 86 post), 688 nodes, every tensor 24 floats wide. `ggml_cuda_try_fuse` now matches the chain and
runs one kernel over `hc*n_tokens` floats that writes the same tensor the SCALE node writes, so the HC ops
and every other reader are untouched.

**Two things stopped the matcher, both found without a model load.** `.scratch/hc-order.cpp` rebuilds the
block outside the model against ggml-base alone and dumps the node order, which is seconds a turn instead of
a 20 minute load:

   5 MUL        (mixes view * scale)
   6 VIEW       (the hc_base view)
   7 ADD        8 UNARY(SIGMOID)   9 SCALE    10 DSV4_HC_PRE

- the window is **five** nodes, not six: the base view is the ADD's second source and is visited between the
  MUL and the ADD, and the SCALE is the last node of the chain either way (nothing else can be visited after
  it, since it is the last node of its own subtree);
- `ggml_can_fuse_subgraph` rejects any window holding a view of a weight. Its check is
  `ggml_is_constant(view_src)`, which requires the source's buffer to carry `GGML_BACKEND_BUFFER_USAGE_WEIGHTS`,
  and the buffers the meta backend hands the device do not: the check returns false for every such window, and
  the matcher had to be given a private copy of those checks that accepts a view source that is a leaf
  (`op == GGML_OP_NONE`) instead.

The first point is why the 2026-09-16 entry above, and `docs/targets.md` before it, could be right that the
fusion "is not absorbing them" without the reason being the pattern; the second is a wider finding than this
change, since every existing CUDA pattern whose window holds a view of a weight is rejected the same way.

**Bit-exactness is the correctness property, and it is testable here.** The first kernel let the compiler
contract `mixes*scale + base` into an FMA, which is one rounding fewer than the two kernels it replaces; the
accepted length moved from 4.52 to 4.02 and only the arm with the fold moved. With `__fmul_rn`/`__fadd_rn`
and the sigmoid written as `unary.cu` writes it, the accepted length is 4.52 in all thirty reps of both arms.
Recorded with it: **`mean len` is not reproducible across loads.** The same no-fold arm read 4.32 in one load
and 4.52 in the next, so the acceptance figure is a within-load check only, and a change that moves it must be
re-checked for bit-exactness rather than judged by the figure.

Measurement, fifteen rotated rounds, both metrics, graphs off, switch is
`GGML_CUDA_HC_GATE_SWITCH` naming a marker file (unset means folded, which is the landed default):

| arm | ms a token, median | tok/s, median | accepted length |
|---|---|---|---|
| chain as built | 26.04 | 37.4 | 4.52 in 15 of 15 |
| chain folded | **25.82** | **37.7** | 4.52 in 15 of 15 |

Gates pass on the first arm (`Paris. The capital of Spain`, `72, 9x9`). The instrument counted 335,000 folds
over the on arms, all of them on the client and none on the peer, so the chains are not split across the
tensor-parallel boundary.

**What that buys, and what it prices.** 516 launches of 6,295 removed, 8.2 %, read 0.84 % of ms a token, which
is 1.0 ms of a 117 ms pass: **about 2 us a launch, not the 10 us the host figures implied.** That is the
useful part of this entry. The host is not the constraint, so removing a launch is worth the device's
retire-and-start, ~2 us, and no more. The launch-rate entry above priced fusion at "launches removed times
~10 us" and put the whole 4,770-kernel small pile at 48 ms of host; the honest price is ~9 to 12 ms for the
whole pass, so the maximum in fusion is ~10 % rather than the ~20 % that arithmetic allowed, and this fold is
where that rate is now measured instead of derived.

The change is landed as the default in `ggml/src/ggml-cuda/ggml-cuda.cu` (`ggml_cuda_match_hc_gate`,
`ggml_cuda_op_dsv4_hc_gate` in `ggml/src/ggml-cuda/dsv4-hc.cu`, `ggml_cuda_op_dsv4_hc_gate` declared in its
header) with `GGML_HC_GATE_STATS` printing the fold count and the distinct reasons a chain is not folded.

--- 2026-09-16, the draft's 20.6 ms is 13 ms of decode and 3 to 6 ms of CPU sampling, and the sampler's fallback is why ---

`GGML_DRAFT_PROF` on the tensor-parallel arm, one 512-token rep, four prints:

|---|---|---|---|
| marginal | 13.1 - 14.0 ms | 2.9 - 6.0 ms | 15.4 - 19.9 ms |

So the draft's wall time, 17 to 20 ms a pass, is not one thing: the decode is 13 ms and the host-side

The same run printed a 429-node and a 27-node graph besides the 9,322- and 9,346-node prompt graphs. 429

**A correction this forces on the kernel count.** The 2026-09-16 entry "the kernel count stands" divided

--- 2026-09-16, the draft's block sampling read as an argmax: identical tokens, 4 % off the pass ---

Since both block-reading paths take the highest-logit candidate rather than a draw, the token is the
argmax of the draft's logits, and the whole candidate array and sort are avoidable. A local
`ggml_draft_argmax` reads it straight off the logits, behind `GGML_DRAFT_GREEDY_SWITCH` (absent means
the sampler chain, unset means the argmax, which is what landed).

**The first version was slower, and that is the calibration.** It computed the softmax denominator at the
argmax to return the probability alongside the token, and paid for it:

| arm | ms a token, median | tok/s, median | accepted length |
|---|---|---|---|
| sampler chain | 25.80 | 37.8 | 4.52 in 15 of 15 |
| argmax, two passes | 26.85 | 36.4 | 4.52 in 15 of 15 |

Bit-identical in output and 4 % slower: that second pass is 129,280 `expf` calls at each of five block
positions, 646,400 a pass, about 4.6 ms of a 117 ms pass, and the regression is exactly that size. So the
host-side sampling costs 4 to 6 ms and the exponential is most of it. Only the DFlash1 path reads the
probability, for its `p_min` check, and the DSpark path never does.

With the denominator computed only when a caller needs it:

| arm | ms a token, median | tok/s, median | accepted length |
|---|---|---|---|
| sampler chain | 26.65 | 36.5 | 4.52 in 15 of 15 |
| argmax | **25.56** | **38.0** | 4.52 in 15 of 15 |

**-4.1 % on ms a token, +4.1 % on tok/s, 10 of 15 rounds to the argmax**, gates passing, and the accepted
length is 4.52 in all thirty reps, so the drafting is token-for-token what it was: the sampler chain was
being asked for a value only one of its consumers ever looked at. This is the second largest measured win
of this session after CUDA graphs, and it is not a kernel: it is four thousand lines of llama.cpp's
sampler machinery avoided five times a pass.

What it does not do is remove the *reason* the fallback exists. The draft's sampling would be free if the
sampler ran on the device, and `common/speculative.cpp` already asks for that; the refusal is

the change with the larger prize left in it, since it would remove the 2.6 MB of logits the host reads and
the single pass this change still makes over them.

--- 2026-09-16, the fusion switch was biased, and fusion is worth 0.6 % a pass, not 10 % ---

`GGML_CUDA_FUSION_OFF_PATH` is the switch every fusion measurement in this record used, and it was read

**Per pass, fusion is worth 0.6 %**, which is a wash; per *token* it looks like 3 % and that is entirely

--- 2026-09-16, CUDA graphs are worth +7 %, and the entry that disabled them tested one configuration twice ---

- **The reversals are all in the same direction: this record's negative results measured with fewer than

--- 2026-09-17, the MoE grid-order effect is not reproducible across loads: three runs, two signs ---

The entry above lands the swap at +6.6 %. Three runs of the same protocol, on the same build, in the same
session, do not agree on its sign, and the change is therefore reverted to the upstream ordering.

| run | arms | comparison | ms a token | verdict |
|---|---|---|---|---|
| 1 | client's grid swapped, peer as-is vs both as-is | swap on the client | 24.01 vs 25.72 | -6.6 %, 12 of 15 rounds |
| 2 | both swapped vs both as-is | both nodes | 26.54 vs 25.29 | **+4.9 %**, 8 of 14 rounds |
| 3 | three arms, order rotated, 12 rounds | both vs as-is | 23.81 vs 26.09 | -8.72 % |
| 3 | same run | client's grid only vs as-is | 25.42 vs 26.09 | -2.55 % |

Run 3 separates the two nodes and says most of the effect is the peer's grid (both -8.7 %, client alone
-2.6 %), while run 1 said the client's alone was worth -6.6 % and run 2 said doing it on both was a 4.9 %
loss. Every one of those measurements used the rotated within-load protocol, `mean len` read per arm
(4.52 everywhere), and the same two marker files.

**What that means.** A change whose sign flips between loads cannot be landed, whatever any single run
says, and the earlier entry's inference from run 1 ("the issue order does matter, which is the effect the
grouped kernel would capture") is withdrawn with it: the grouped kernel's case goes back to being the
record's arithmetic about issued traffic, not a measurement. The likeliest mechanism for the instability
is that the effect is a memory-locality one, and the physical placement of the expert tensors is decided
by the allocator afresh on every load, so a change that trades issue order for locality can come out
either way depending on addresses. If that is right, the whole class of "reorder the reads" changes on
this rig is unmeasurable at this size, and the only honest way to take the MoE's redundancy on is the
grouped kernel, which removes the rereads rather than rescheduling them.

**And it prices this record's protocol honestly.** Three runs, fifteen rotated rounds, identical
acceptance, and a 5 to 9 % effect that changes sign: that is the resolution limit of a *single* run for
effects of this class. The two results in this session that are not of this class are the ones with an
independent reason to be believed, the CUDA graphs default (whose predecessor A/B provably never enabled
the graph path at all) and the draft argmax (bit-identical drafting in all thirty reps of its A/B). Both
of those also measured 4 to 7 %, so the lesson is not that everything here is noise; it is that a
measurement of this size needs a mechanism that does not depend on where the allocator put the weights.
